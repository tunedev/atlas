# The postings feed — design

**Supersedes nothing.** This design details Epic 5 of `docs/plans/2026-09-17-roadmap.md`
and sits under `docs/specs/2026-09-17-job-hunt-harness-design.md`, whose topology it
implements: a public feed the app pulls as a `Source`, over a git remote, and never
operates.

**Goal:** unattended discovery without a backend, and story 5.8 — no user data reaches the
feed, ever — true by construction rather than by policy.

## The decision this rests on

The feed is a new, public, sibling repository beside `atlas` and `infra`, called `feed` in
this document. It holds normalised postings and nothing else. A scheduled GitHub Action,
running on free public-repo runners, is its only writer. `atlas` is a reader: it pulls
`feed` like any other git remote and never pushes to it. That asymmetry is what makes
5.8 structural — see "Why 5.8 is structural" below, not a promise enforced by review.

`feed` is its own Go module, `Go end to end` per the Forge constraint, and is not part of
`atlas`'s module or its architecture tests. `internal/arch/vocabulary_test.go` walks only
`atlas`'s tree; `feed` is free to use the word "posting" everywhere, because it is not the
harness. The one place the two worlds touch is the `Source` port in `atlas`, addressed
explicitly below.

## 5.1 — The normalised posting schema

One JSON object per posting, one file per posting. Fields:

| Field | Type | Meaning |
|---|---|---|
| `schema_version` | integer | Shape of this document. See versioning below |
| `id` | string | `<source>/<board>/<external_id>`, matches the file's path |
| `source` | string | `greenhouse`, `lever`, `ashby`, `workable`, `remoteok` |
| `board` | string | The company/board slug at that source |
| `company` | string | Display name |
| `title` | string | Role title |
| `location` | string | Free text, as the board gave it |
| `remote` | boolean | Best-effort, from the board's own remote flag or location text |
| `url` | string | The board's own posting URL |
| `description_text` | string | Plain-text body |
| `description_html` | string | Original HTML body, when the board provides it |
| `posted_at` | string, RFC 3339 | When the board says it was posted, if it says |
| `fetched_at` | string, RFC 3339 | When this crawl observed it |
| `status` | string | `open` or `removed` — see repo layout |
| `removed_at` | string, RFC 3339, optional | Set once, when `status` becomes `removed` |
| `render_status` | string | `static`, `rendered`, `needs_rendering`, or `error` — 5.5 |

### Example document

```json
{
  "schema_version": 1,
  "id": "greenhouse/gitlab/7192161",
  "source": "greenhouse",
  "board": "gitlab",
  "company": "GitLab",
  "title": "Backend Engineer, Distribution",
  "location": "Remote",
  "remote": true,
  "url": "https://boards.greenhouse.io/gitlab/jobs/7192161",
  "description_text": "We are looking for...",
  "description_html": "<div>We are looking for...</div>",
  "posted_at": "2026-09-20T00:00:00Z",
  "fetched_at": "2026-09-24T06:00:00Z",
  "status": "open",
  "render_status": "static"
}
```

### Versioning

`schema_version` is a per-document integer, not a repo-wide guarantee — because `feed`
holds current-state files, not an append-only log, two documents on `main` can carry
different versions during a migration. It starts at 1 and increments only on a breaking
change: a field renamed, removed, or retyped, or the addressing scheme changing.

A consumer pins by git ref (branch or tag), configured in `atlas`, not by the integer
alone. Two pinning modes, and both are real:

- **Pinned to `main` (the default).** The consumer sees whatever `main` currently holds,
  including a migration in flight, and tells old from new shape by reading
  `schema_version` per document — the field exists precisely so this is decidable without
  re-cloning or asking the repo's own version.
- **Pinned to a tag.** Before a breaking migration lands, the commit immediately prior is
  tagged (e.g. `pre-v2`). A consumer pinned to that tag is frozen: unaffected by the
  migration, but also unaffected by every crawl after it — no new postings either. Moving
  the pin forward is a deliberate, later action.

There is no attempt to keep two live, permanently-diverging branches (a v1 branch and a v2
branch both receiving fresh crawls forever). That is real machinery for a feed with one
consumer today; a tag freeze plus the per-document field is the whole mechanism, and it is
cheap because a migration is rare and the crawl only ever writes to one lineage.

**What happens to a consumer when the version changes:** nothing, until the consumer acts.
The `Source` port (5.6) passes each posting's body through as opaque bytes — the core
never parses it — so a version bump cannot break `atlas`'s Go tree; it can only break a
pack template that reads a field by name. That break is visible (a missing field renders
empty, per the harness's existing template-selection behaviour) and is fixed by updating
the pack, not the port.

## Repo layout

```
feed/
  postings/<source>/<board>/<external-id>.json
  status/<source>/<board>.json
  runs/<crawl-timestamp>.json
  boards.yaml
  schema/v1.md
  CHANGELOG.md
  cmd/crawl/main.go
  internal/fetch/{greenhouse,lever,ashby,workable,remoteok}/
  internal/normalize/
  internal/commit/
  .github/workflows/crawl.yml
```

**Addressing.** A posting's id is `<source>/<board>/<external-id>`, identical to its path
minus the `.json` suffix. The id is stable for as long as the board keeps the same
external id, and is duplicated inside the document's own `id` field so a consumer holding
only the bytes still knows the document's address.

**History is kept per posting, not per crawl.** `postings/<source>/<board>/<id>.json` is
one file; every crawl that changes it is one commit touching that file, so `git log` on
the file is the posting's own revision history. There is no per-crawl snapshot directory —
duplicating every unchanged posting on every run would grow the repo for no reason.

**A crawl gets a manifest, not a snapshot.** `runs/<timestamp>.json` records what happened
in one crawl: which fetchers ran, how many postings each returned, and any error — see
5.3. It is metadata about a run, never a copy of the data.

**A vanished posting is not one that never existed.** When a crawl no longer sees a
previously known id, the file is not deleted. It gets one more revision: `status` becomes
`"removed"`, `removed_at` is set, and every other field keeps its last observed value.
Deleting the file at that point would collapse "closed" into "never posted." A `removed`
file is deleted from `main` only after it has held that status for a retention window
(90 days, a config value in `cmd/crawl`, not load-bearing to this design) — a housekeeping
step in the same workflow, committing a plain deletion. Git history still has it; only the
current tree loses it, which is what keeps the repository bounded.

## 5.2 — The fetchers

| Board | Endpoint | Auth | Per-board quirk |
|---|---|---|---|
| Greenhouse | `GET boards-api.greenhouse.io/v1/boards/{token}/jobs?content=true` | none | One call returns the whole board; `content=true` inlines HTML, else a second call per job is needed |
| Lever | `GET api.lever.co/v0/postings/{site}?mode=json` | none | EU-hosted accounts live under `api.eu.lever.co` — a per-company host flag, not a URL constant |
| Ashby | `GET api.ashbyhq.com/posting-api/job-board/{jobBoardName}?includeCompensation=true` | none | One call per board; no filtering or pagination available |
| Workable | `GET apply.workable.com/api/v1/widget/accounts/{subdomain}` | none | Some accounts omit full descriptions from the list call; a `?details=true` follow-up per job may be required |
| RemoteOK | `GET remoteok.com/api` | none, but a descriptive `User-Agent` is required or Cloudflare blocks the request | One global feed, no per-company slug; the first array element is a legal notice, not a job, and must be skipped |

All five are unauthenticated, keyless, public JSON endpoints. None needs a secret, which
removes an entire class of leakage from the Action's logs.

None of the five publish a directory of companies that use them. `boards.yaml` is a
hand-curated seed list of `{source, slug}` pairs — the crawl's actual coverage is exactly
this list, and growing it is a config change (adding a line), never a code change.

```go
// Fetcher pulls one board's current postings and maps them into the
// normalised schema. Fetch does no writing; the caller diffs and commits.
type Fetcher interface {
    Name() string
    Fetch(ctx context.Context) ([]Posting, error)
}
```

Applying the calibration rule honestly: five real boards, and a plausible sixth
(SmartRecruiters, BambooHR) later, is what earns `Fetcher` a place as an interface rather
than five unrelated functions. The shared code is one function — a bounded, timed JSON GET
(`internal/fetch/httpjson`, the same shape as `tools.HTTP`'s `readLimited` in `atlas`) —
not a second interface, because there is exactly one plausible way to do a bounded JSON
GET. Everything else is per-board: the response struct, the mapping into `Posting`, and
the quirk in the table above. The port buys reuse of the GET-and-decode plumbing and a
uniform place to plug in a sixth board; it does not buy a shared response shape, because
the five boards do not have one.

## 5.3 — The scheduled Action

```yaml
on:
  schedule:
    - cron: "0 */6 * * *"
  workflow_dispatch: {}
jobs:
  crawl:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: "1.27" }
      - run: go run ./cmd/crawl
      - run: |
          git config user.name "feed-bot"
          git config user.email "feed-bot@users.noreply.github.com"
          git add postings status runs
          git diff --cached --quiet || git commit -m "crawl $(date -u +%FT%TZ)"
          git push
```

Every six hours, plus `workflow_dispatch` for an on-demand run (this is also how the Action
is tested — see Testing). `ubuntu-latest` is a standard runner: GitHub Actions is free for
public repositories on standard runners with no minute cap, so nothing here bills, ever.

**Partial failure.** `cmd/crawl` runs every `Fetcher` independently, catching each one's
error rather than letting it abort the run. It always writes `runs/<timestamp>.json` and
each fetcher's `status/<source>/<board>.json`, whatever succeeded or failed, and commits
whatever changed. The process exits non-zero — failing the Action visibly in GitHub's UI —
only when every fetcher failed. One board being down is the expected, unexceptional case
and is visible only in that board's own `status/` record; all five failing is exceptional
and should page.

`ubuntu-latest` ships Google Chrome preinstalled, which is what makes 5.4 free: Rod's
`launcher.LookPath()` finds it directly, and the crawl never downloads a browser.

## 5.4 / 5.5 — Rendered sources and the needs-rendering signal

Rendering runs inside `cmd/crawl`, in the same Action, using Rod against the Chrome the
runner already has. `Race` handles the cookie-banner-or-content-or-interstitial problem
per the harness spec.

The failure mode this exists to prevent is silent zero: an HTTP-only fetch of a
JavaScript-rendered careers page returns an empty shell and looks, to naive code, like a
board with no open roles. The signal must exist even when there are zero postings to
attach it to, so it cannot live only on posting documents. It lives in
`status/<source>/<board>.json`:

```json
{
  "source": "rendered",
  "board": "acme-corp",
  "render_status": "needs_rendering",
  "checked_at": "2026-09-24T06:00:00Z",
  "posting_count": 0
}
```

`render_status` values: `static` (a structured-board fetch, never needed rendering),
`rendered` (Rod ran and extracted postings), `needs_rendering` (an HTTP-only probe found an
empty or JS-only shell and Rod has not yet resolved it, or Rod itself found nothing),
`error` (Rod ran but extraction broke — the page's structure likely changed). Every
posting produced by a rendered fetch also carries `render_status: "rendered"` on the
document itself, so a consumer never has to cross-reference the status file to know how a
given posting was obtained.

## 5.6 — The `Source` port in atlas

The tension named up front: `atlas`'s Go tree may not name a use-case concept, and this
port is the one place a use-case-shaped feed meets the harness. It is resolved the same
way `Docs` already resolves it for arbitrary documents — the port speaks paths and bytes,
never what the bytes mean.

```go
// Item is one document a Source yields, addressed by ID. Body is opaque —
// the core does not parse it, the same way Docs never parses what it stores.
// A pack narrows Body by path, the way it already narrows any tool's result.
type Item struct {
    ID   string
    Body []byte
    When time.Time
}

// Source answers what is there now, and how fresh that answer is. Pull
// returns every item present; nothing about "new since last time" is the
// port's concern, so a git remote, a local crawler, and a rendered fetch
// all answer the same two questions the same way.
type Source interface {
    Pull(ctx context.Context) ([]Item, error)
    LastRefreshed(ctx context.Context) (time.Time, error)
}
```

No word here is forbidden by `vocabulary_test.go`, and none needs to be: `Item`, `Body`,
and `Pull` say nothing about postings, boards, or companies. The schema in 5.1 — `title`,
`company`, `schema_version`, all of it — lives inside `Body`, exactly as `feed` wrote it,
untouched by the core. A pack that names `title` and `company` is doing exactly what packs
are for; the port carrying that vocabulary would not be.

**Reading the git remote.** The adapter (`internal/adapters/outbound/feedsource`, mirroring
`gitdocs`'s shape and its choice of `go-git/v5` per the existing convention) never clones
the full history — `Pull`'s contract is "what's there now," and the feed's own history is
`feed`'s business, not `atlas`'s. First use does a shallow, single-branch clone
(`Depth: 1`, pinned `ReferenceName`) into a local cache; every later `Pull` does a shallow
`Fetch` and a hard reset of the worktree to the fetched tip. `LastRefreshed` reads the
pinned ref's tip commit time — reliable without opening any particular file, because
`cmd/crawl` commits a run manifest on every crawl, even one that changed no postings.

**Configuration**, layered per Tenet 6, alongside the existing `StoreConfig`:

```go
type FeedConfig struct {
    RemoteURL   string
    Ref         string        // branch or tag; "main" by default
    CachePath   string        // e.g. ~/.atlas/feed-cache, distinct from Store.Root
    PullTimeout time.Duration
    StaleAfter  time.Duration // 5.7
}
```

`CachePath` is never the user's own `Docs` repository — pulling a public feed must not be
able to touch the private record, even by accident of a shared directory.

A `source.pull` tool wraps the port at the composition root, decoding each `Item.Body` and
returning it alongside `_meta.fetched_at` (from `LastRefreshed`) so a pack can select
postings and check freshness from the same call:

```yaml
- id: feed
  tool: source.pull
  with: {}

- id: role
  tool: http.request   # unchanged; a pack may still hit a board directly
  with:
    select: "{{ .steps.feed.items.0 }}"
```

## 5.7 — Staleness

Feed age is `now - LastRefreshed()`. `FeedConfig.StaleAfter` (default 24h — four missed
six-hourly runs of slack) is the threshold a pack or the app's own summary output compares
it against. "The schedule has stopped" is exactly this number growing past the threshold:
because `cmd/crawl` always commits a manifest, a healthy schedule keeps the pinned ref's
tip time within one crawl interval of now, and a stopped one falls behind monotonically,
with no separate heartbeat mechanism needed. The `source.pull` tool exposes
`_meta.age_hours` so a pack decides what to do with staleness (warn, skip scoring, refuse
to draft) — the threshold judgement is use-case-shaped and belongs in a pack, not in Go.

## Why 5.8 is structural

`feed`'s only writer is its own scheduled Action, authenticated as the repository's own
identity, running code that touches exactly three paths — `postings/`, `status/`,
`runs/` — with data read from five public, keyless board APIs. `atlas` opens the
relationship the other way: `Source.Pull` and `LastRefreshed` only ever `git fetch`,
never `git push`. There is no webhook, no CI secret shared between the two repos, no
telemetry call from the app into the feed, and nothing that would let an "applied" or
"skipped" decision, a CV, or a preference travel from a user's machine into a commit in
`feed`. The guarantee is not a review checklist item; it is that no code path exists to
violate it. A test asserting "no field in `postings/**/*.json` matches a name from the
user-data schema" is a useful tripwire, but the structural fact is the one-directional
git relationship, not the test.

## Testing

- **Fetchers**, offline: each board's response is a recorded fixture JSON file, served by
  `httptest.Server`. The fetcher's mapping is asserted against it, including the quirk —
  RemoteOK's first-element skip, Workable's missing-description flag, Lever's EU host.
- **Commit and diff logic**, offline: exercised against a temporary git repository built
  by the test (the same pattern `gitdocs`'s tests already use with `t.TempDir()`), never
  the real `feed` remote.
- **The Action, without waiting for a schedule:** `workflow_dispatch` lets a human or a CI
  job trigger a real run on demand. Separately, `go run ./cmd/crawl -dry-run` runs the same
  fetch-normalise-diff pipeline locally against the recorded fixtures, so the pipeline's
  logic runs in every PR to `feed`, not only on the cron.
- **The `atlas` `Source` adapter**, offline: tested against a temporary bare repository
  the test creates and pushes fixture postings into, asserting `Pull` reflects the pinned
  ref's tip and `LastRefreshed` matches that commit's time. No network.

## Deliberately not in this increment

| Out | Why |
|---|---|
| Local crawling (Colly), rendering opt-in on the user's machine | Epic 8; this epic covers only the feed |
| Deduplication across sources (board vs. aggregator vs. company page) | Epic 8.5, and it needs this epic's schema decided first, per the roadmap's sequencing |
| LinkedIn, Hacker News "Who's Hiring", boards beyond the five named | Not committed to; `Fetcher` and `boards.yaml` leave room, no story asks for them yet |
| A company-slug discovery service | None of the five expose one; `boards.yaml` stays hand-curated |
| The app rendering a posting's full git history | Nothing in Epic 5 asks the app to show history, only current state; the history exists in `feed` and is unconsumed for now |
| Two permanently-diverging schema-version branches | Rejected as overengineering for a feed with one consumer; a tag freeze plus the per-document `schema_version` field is the whole mechanism |
| Retry/backoff/circuit-breaking on the five board APIs | A crawl that runs every six hours and skips a failed board this cycle already gets the resilience a breaker would buy; Tenet 3 machinery is for a dependency called on a live request path, which this is not |
| Authenticating to any board or career page | Never; all five are public and keyless, matching Epic 8.6's rule even though that story is nominally Epic 8's |

## Open questions

- **Scheduled workflows on an otherwise-idle repository.** The harness spec already flags
  that GitHub disables scheduled workflows after a period of inactivity, and that a
  workflow's own commits may or may not count as activity. `feed` commits on its own
  schedule, so this either holds or it does not — verify once the repository exists;
  design here assumes it does.
- **Curating `boards.yaml`.** No roadmap story assigns who adds a company, or how — a
  hand-edited file today, possibly PR-driven later.
- **The 90-day retention window** before a `removed` posting's file is deleted is a
  placeholder default, not a considered number; it lives in `cmd/crawl`'s config, not in
  this design.
