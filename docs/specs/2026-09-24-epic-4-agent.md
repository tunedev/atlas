# The `Agent` port, over ACP — design

**Supersedes nothing.** This design details Epic 4 of `docs/plans/2026-09-17-roadmap.md` and
sits under `docs/specs/2026-09-17-job-hunt-harness-design.md`, whose "two kinds of thinking,
two kinds of port" section already establishes `Agent` as the doer's port. This spec settles
how it is built.

**Goal:** drive a real coding agent, over its published client protocol, so a pack step can
delegate multi-step conversational work — research, drafting, tool use — to the agent the
user already runs, while our own tool registry, permission policy and observability stay in
control of what that agent is allowed to touch.

## Verified before designing

The roadmap names Gemini CLI for story 4.7's evidence. The human has chosen **Claude Code**
instead. Both are ACP-agent choices, not architecture choices, but the facts below had to be
established before any of this could be designed rather than guessed at.

### What ACP specifies

Source: `https://agentclientprotocol.com` (spec and docs) and the reference implementations at
`https://github.com/agentclientprotocol/*` — `typescript-sdk`, `rust-sdk`, `python-sdk`,
`kotlin-sdk`, `java-sdk`. **No `go-sdk` repository exists** (confirmed: `GET
/repos/agentclientprotocol/go-sdk` returns 404). The harness spec's claim that we implement
the subset we need, by hand, against the schema, is correct and still holds.

| Area | What the spec says |
|---|---|
| Transport | JSON-RPC 2.0 over stdio. The agent runs as a subprocess of the client. Messages are newline-delimited JSON — "delimited by newlines (`\n`), and MUST NOT contain embedded newlines." No Content-Length framing. |
| stdout/stderr | "The agent MUST NOT write anything to its stdout that is not a valid ACP message." The agent MAY write UTF-8 to stderr for logging. Stdout is the wire; stderr is diagnostics. |
| Initialisation | Client sends `initialize` with `protocolVersion` (integer, major version), `clientCapabilities`, `clientInfo`. Agent responds with `protocolVersion`, `agentCapabilities` (`loadSession`, `promptCapabilities`, `mcpCapabilities`), `agentInfo`. |
| Version mismatch | If the agent does not support the client's version it MUST respond with the latest it does support. If the client does not support the version the agent named, the client SHOULD close the connection and tell the user. Nothing about this is negotiated mid-session. |
| Session creation | `session/new` — client sends a working directory and MCP servers, agent returns a session id. |
| Session resume | `session/load`, gated by `agentCapabilities.loadSession`. The agent replays the **entire** conversation history via `session/update` notifications before the `session/load` call itself returns. A finer-grained `sessionCapabilities.resume` also exists for reconnecting without replay, but is not universally implemented. |
| Prompt turn | `session/prompt` (client to agent) is the request; the agent streams `session/update` notifications (message chunks, `tool_call`, `tool_call_update`, plan) and the original `session/prompt` call itself resolves with a stop reason when the turn ends. `session/cancel` interrupts. |
| Tool calls | Reported via `session/update` of type `tool_call`: `toolCallId`, `title`, optional `name`, `kind` (`read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`), `status` (`pending` → `in_progress` → `completed`/`failed`), `content`, `locations`, `rawInput`/`rawOutput`. Later `tool_call_update` notifications carry only changed fields. |
| Permission requests | `session/request_permission` (agent to client): carries the tool call and a set of options (`allow_once`, `allow_always`, `reject_once`, `reject_always`). Client responds with the selected option or `cancelled`. |
| Agent-initiated I/O | The agent may call back into the client for `fs/read_text_file`, `fs/write_text_file`, `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/kill`, `terminal/release`, `elicitation/create`. |

This confirms every clause of roadmap stories 4.1–4.6 has a real protocol feature behind it:
JSON-RPC/stdio (4.1), version negotiation that fails loudly (4.2), session lifecycle (4.3),
tool calls and permission requests routed through the client (4.4, 4.5), and session resume
with a documented, if partial, guarantee (4.6).

### Whether Claude Code can be an ACP agent

Established directly on this machine and against the npm registry:

- `which claude` → `/home/tunedev/.local/bin/claude`, version `2.1.281`. `claude --help` has
  no ACP mode or flag. `claude mcp` exists (Claude Code can be an **MCP** client/server), but
  MCP and ACP are different protocols with different roles — MCP connects a model to tools,
  ACP connects an editor/client to a coding agent.
- **Claude Code does not speak ACP natively.** The bridge is a separate published package,
  `@agentclientprotocol/claude-agent-acp` (npm, bin `claude-agent-acp`), built on
  `@anthropic-ai/claude-agent-sdk` (the TypeScript Claude Agent SDK) and
  `@agentclientprotocol/sdk`. It was previously published as
  `@zed-industries/claude-code-acp`, now deprecated in favour of the current package name; the
  npm registry marks the old name "DEPRECATED — renamed to
  @agentclientprotocol/claude-agent-acp."
- **It is not published by Anthropic.** Its maintainers (`aguzubiaga`, `benbrandt`, `cirwin`,
  plus former Zed maintainers) are the same people who publish the ACP spec and SDKs; the
  package lives in the `agentclientprotocol` GitHub org alongside `codex-acp` (an equivalent
  bridge for OpenAI's Codex CLI). It is a third-party adapter process, not a mode of Claude
  Code itself.
- **Nothing ACP-related is installed on this machine.** `claude-code-acp` is not on `PATH`.
  Running the bridge would mean installing Node.js/npm tooling (already assumed present for a
  TypeScript package) plus the package itself (`npm install -g
  @agentclientprotocol/claude-agent-acp` or invoking it via `npx`), which in turn pulls in
  `@anthropic-ai/claude-agent-sdk`, `@agentclientprotocol/sdk`, `@modelcontextprotocol/sdk`
  and `zod`.

**Stated plainly:** Claude Code cannot serve as an ACP agent on its own. It can only do so
through this adapter subprocess, which is itself a real, versioned, third-party dependency —
one more moving part than Gemini CLI, which the roadmap describes as speaking ACP directly (a
claim this spec did not re-verify, since it is not the chosen path, but nothing in the design
below depends on it being true).

### The consequence for this design

Atlas's own code must not encode an opinion about which of these is running. The `Agent`
port's adapter is a generic ACP client over a **configured subprocess command** — argv,
working directory, environment. Whether that command is `claude-agent-acp`, `gemini
--experimental-acp`, `codex-acp`, or a test stub is a config line, exactly like
`ModelConfig.BaseURL` already makes the model vendor a config line rather than a Go type. The
harness spec's port table (`Agent` | Gemini CLI over ACP | Claude Code via its ACP adapter)
described two rows of the same adapter, not two adapters; this design makes that explicit.

**Divergence from the roadmap, recorded rather than silently edited:** story 4.7 as written
says *"Gemini CLI, end to end, evidence pasted."* The evidence this epic will actually produce
is Claude Code, end to end, through `@agentclientprotocol/claude-agent-acp`, evidence pasted —
because that is the agent the human chose to run first, and because the config-driven design
above makes either a config change, not a rewrite. Whoever plans the implementation should
treat 4.7's acceptance text as amended to name the configured agent rather than Gemini CLI
specifically, and should install the adapter package themselves (see Testing, below) rather
than have an agent session attempt a live npm install.

## What this rests on

Epic 0–3 shipped: `ports.Tool` and `ports.Registry` (`internal/core/ports/ports.go`), a
blueprint `Runner` that resolves a step's tool, renders its config, invokes, narrows and
traces (`internal/core/app/runner.go`), a YAML pack loader (`packfile.Load`), and `ports.Judge`
as the most recent example of a core port with two nameable adapters. `cmd/atlas/main.go`
remains the only file that knows every concrete type, and its tests (`TestBuildRegistry
RegistersBothShippedTools`, `TestBuildRegistryRegistersTheJudgeTool`,
`TestBuildRegistryPassesNoLiterals`) are the shape a fourth port's wiring must fit: registered
in `buildRegistry`, resolvable by name, and built from `cfg` fields with no literal of its own.

## Where ACP sits in the hexagon

Both directions the tenets ask about exist inside **one** adapter, because ACP itself puts
both roles in one subprocess conversation:

- **We drive the agent.** A pack step wants work done; that is a core need, so the core owns
  an outbound port for it (`ports.Agent`), the same shape as `Provider` and `Judge`.
- **The agent drives us.** While doing that work, the subprocess calls back for tool
  execution and permission decisions. That is not a second port for "an agent calling us" —
  it is the adapter's own responsibility to satisfy those callbacks using ports the core
  *already* owns: `ports.Registry`/`ports.Tool` for tool calls, and a new `ports.Permission`
  for authorization decisions. No pack, tool or blueprint concept crosses into the adapter;
  no ACP concept crosses into the core.

```
core/app  ---Do(ctx, task)--->  adapters/outbound/acpagent  <--stdio JSON-RPC-->  agent subprocess
    ^                                   |    |
    |                                   |    +--session/request_permission--> ports.Permission
    |                                   +--tool_call---------------------------> ports.Registry -> ports.Tool
    +---------------AgentUpdate stream (core vocabulary)------------------------+
```

`ports.Registry` is not duplicated or wrapped in ACP vocabulary — the adapter holds the same
`ports.Registry` instance `cmd/atlas` already builds for the pack runner, so a tool the agent
can reach is exactly the set of tools a pack step can reach, registered once.

A port exists where a second implementation is nameable:

| Port | First | Second |
|---|---|---|
| `Agent` | ACP subprocess adapter, configured for Claude Code via `claude-agent-acp` | the same adapter, configured for Gemini CLI or Codex |
| `Permission` | a config-rule engine (allow/ask/deny by tool name and kind) | an interactive terminal prompt |

Only one `Agent` adapter is written. "First" and "second" name configurations of it, which is
the point: the port makes the agent a line in `config.Config`, not a Go type.

## Core types

In `internal/core/ports`, in the core's vocabulary. Nothing here names ACP, JSON-RPC, or a
message shape; `internal/arch/vocabulary_test.go` and the existing architecture test both hold
unchanged.

```go
// AgentTask is one unit of delegated work: a prompt and the directory the
// agent may act in. WorkDir is a real path, not a repo-relative one --
// the agent process owns nothing outside it that we grant through tools.
type AgentTask struct {
    Prompt  string
    WorkDir string
}

// AgentEvent is one step of progress, in Atlas's own vocabulary. Kind names
// what the caller can act on; a pack step reports it, it does not parse it.
type AgentEventKind string

const (
    AgentEventMessage  AgentEventKind = "message"
    AgentEventToolCall AgentEventKind = "tool_call"
    AgentEventPlan     AgentEventKind = "plan"
)

type AgentEvent struct {
    Kind AgentEventKind
    Text string
}

// AgentResult is what a task produced and why the agent stopped.
type AgentResult struct {
    Text       string
    StopReason string
}

// Agent drives a coding agent through one turn of work. onEvent is called
// synchronously, in order, for every update the agent reports before Do
// returns; a slow or panicking onEvent therefore blocks or crashes the
// caller's own goroutine, never a hidden one owned by the adapter.
//
// SessionID, when non-empty, resumes a session this Agent produced before;
// empty starts a new one. The returned SessionID is set whether or not one
// was passed in, so a caller that wants to resume later always has one to
// keep.
type Agent interface {
    Do(ctx context.Context, task AgentTask, sessionID string, onEvent func(AgentEvent)) (result AgentResult, newSessionID string, err error)
}

// PermissionRequest is one decision an agent-invoked tool call needs before
// it runs. ToolName is the registry name being called, never an ACP id;
// Summary is a short, bounded description of what it would do -- a title
// and, when it fits a fixed budget, a rendering of its arguments.
type PermissionRequest struct {
    ToolName string
    Summary  string
}

type PermissionDecision string

const (
    PermissionAllow PermissionDecision = "allow"
    PermissionAsk   PermissionDecision = "ask"
    PermissionDeny  PermissionDecision = "deny"
)

// Permission decides whether one tool call an agent requested may run.
// Ask means the underlying engine could not decide by policy alone and is
// itself asking a human; an engine that always resolves to allow or deny
// never returns Ask.
type Permission interface {
    Decide(ctx context.Context, req PermissionRequest) (PermissionDecision, error)
}
```

`Agent` is one method, matching the "narrow port" rule: session lifecycle (new vs. resume) is
a parameter, not four RPCs, because the pack author only ever wants "do this, resuming if I
give you an id" — the ACP-level distinction between `session/new` and `session/load` is an
adapter concern, not a core one.

## The session lifecycle (4.3, 4.6)

| Stage | ACP call | Where it happens |
|---|---|---|
| New | `session/new` | inside `acpagent.Do` when `sessionID == ""` |
| Prompt | `session/prompt` | inside `acpagent.Do`, always |
| Streamed updates | `session/update` notifications | translated to `ports.AgentEvent` and handed to `onEvent` as they arrive |
| Close | closing stdin / process exit | when the adapter itself is closed (see Process lifecycle) |
| Resume | `session/load` | inside `acpagent.Do` when `sessionID != ""`, before the next `session/prompt` |

**Where session state lives:** almost entirely in the agent subprocess, because that is what
`session/load` replays from. Atlas's own responsibility is to remember the *pointer* — the
session id and which agent command produced it — so a later run of atlas can hand it back.
That pointer is a document, through the existing `ports.Docs`, not a new store:

- `agent-sessions/<subject-id>.json` — `{ "session_id": "...", "command": "...", "args":
  [...], "protocol_version": N, "created_at": "..." }`.
- The caller supplies the subject id, the same convention `Judge`'s recording already uses,
  because "which session goes with which pack run" is a use-case fact the core does not
  invent.
- Writing this document is a separate use case in `internal/core/app`, composing `Agent` and
  `Docs`, the same separation `Judge.Ask` keeps from its own recording.

**What "resumes where it stopped" actually guarantees, and what it does not:** `session/load`
guarantees the client receives the full prior conversation — every message and tool call the
agent reported — replayed as `session/update` notifications before the call returns. It does
**not** guarantee that a tool call left `in_progress` when the process died actually completed,
or that any side effect outside the chat transcript (a file write, a spawned process) resumed
or rolled back. A résumé is a correct conversation, not a correct world. Consequently, a pack
step that resumes an agent session must treat any tool call whose last known status was
`pending` or `in_progress` as unverified, and re-check its effect at the blueprint level
(e.g., re-reading the file the agent claimed to write) rather than trusting the replay. This
is a real limit of the protocol, not a gap in this design, and it is why the roadmap calls
epic 4.6 "the A2H seam" rather than "the A2H mechanism": it is where a future
suspend/resume-for-authorization protocol (the `suspend` permission outcome sketched in
`docs/specs/2026-09-09-increment-1-boundaries-design.md`, never built) would attach, and this
increment deliberately does not build that attachment — see Deliberately not in this
increment.

## The tool bridge (4.4)

An agent's `tool_call` update names a tool and carries `rawInput` as arbitrary JSON. The
existing `ports.Tool.Invoke` takes `map[string]string`, because packs render every argument as
a string template. The bridge must reconcile these without teaching `ports.Tool` about JSON:

1. The adapter receives a `session/update` of kind `tool_call` (or, more precisely, the
   `session/request_permission` that normally precedes it — see Permissions below).
2. It maps the ACP tool's declared `name` to a registry name using a fixed, configured table
   (`AgentConfig.ToolNames map[string]string`), never a name the agent invents unchecked —
   an agent asking for a tool with no configured mapping is a `deny`, not a guess.
3. `rawInput`'s top-level fields are flattened to `map[string]string`: each JSON scalar
   becomes its string form; a nested object or array is an error naming the field, because
   silently stringifying `{"a":{"b":1}}` would hide structure a tool needs. No pack in this
   codebase's tools has needed nested arguments; if one eventually does, the pack-facing
   contract (`with map[string]string`) has to change first, and that is a decision for
   whoever needs it, not one this bridge should make unasked.
4. `registry.Lookup` and `tool.Invoke(ctx, with)` run exactly as they do for a pack step. The
   result is serialised back into the `tool_call_update`'s `content` as text; the agent sees
   only the tool's declared name and its textual result, never the Go type, the registry, or
   any pack concept.

This is deliberately the same registry the blueprint runner uses (`cmd/atlas`'s
`buildRegistry`), injected into the ACP adapter at the composition root — "reach the existing
`ports.Tool`" is satisfied by sharing the instance, not by a parallel one.

## Permissions (4.5)

Every ACP `tool_call`, before it runs, produces a `session/request_permission` from the agent
(or the adapter treats an unrequested tool call as needing one anyway — ACP allows an agent to
skip the request for calls it considers safe, and this design does not extend that trust: the
adapter asks `ports.Permission` before invoking any tool regardless of whether the agent
itself asked).

| Piece | Shape |
|---|---|
| Engine | `ports.Permission`, two adapters: a config-rule engine and an interactive terminal prompt |
| Policy | `internal/config`: `PermissionConfig` — an ordered list of `{ToolName string, Kind string, Decision string}` rules, evaluated first match wins |
| Default | `ask`, matching the harness's other allow/ask/deny language (epic 10.2: "default ask; deny beats allow") |
| What a human sees | the tool's registry name, its `kind` (from ACP's enum: read/edit/delete/move/search/execute/…), and a length-bounded rendering of its arguments — never the raw `rawInput` unbounded, per Tenet 5's "bound every payload" |
| Where it's shown | stderr, synchronously, on the terminal — there is no web UI in this epic (epic 12), so the interactive adapter blocks on a `y/n` read from stdin |

Mapping ACP's four options (`allow_once`, `allow_always`, `reject_once`, `reject_always`) to
the three-outcome engine: `allow_once`/`allow_always` both resolve a single `Decide` call to
`allow`; `reject_once`/`reject_always` both resolve to `deny`. "Always" is not persisted across
calls in this increment — every tool call gets its own `Decide`, and promoting a decision into
a standing rule is epic 10.3's job ("a repeated decision can become a rule, promoted
deliberately"), applied later to this engine's config, not invented twice.

**Deliberately not designed here:** the `suspend` outcome and an out-of-band authorization
flow. ACP's `session/request_permission` can be left pending indefinitely by not responding,
which is the seam a later agent-to-human protocol would use — this design notes the seam
exists and does not occupy it.

## Process lifecycle

| Concern | Design |
|---|---|
| Launch | `exec.CommandContext(ctx, cfg.Agent.Command, cfg.Agent.Args...)`, `Dir` set to the task's `WorkDir`. `ctx` is the adapter's own long-lived context, cancelled when `acpagent.Close` runs — never the per-call `ctx` a single `Do` receives, since a subprocess must outlive one prompt to be resumable within the same run. |
| Framing out | Each JSON-RPC message marshalled to one line, `\n`-terminated, written to the subprocess's `stdin`. Never embeds a literal newline — the spec requires this, and `json.Marshal` already produces none. |
| Framing in | A single goroutine, owned by the adapter and started at launch, reads the subprocess's `stdout` with `bufio.Scanner`, one JSON-RPC message per line, dispatching responses to waiting calls by id and notifications to the active `onEvent`. This is the one goroutine ACP's stdout ownership requires; nothing else reads that pipe. |
| Diagnostics | The subprocess's `stderr` is copied, line by line, to Atlas's own logger, prefixed with the agent's configured name. It is not parsed as protocol. |
| Shutdown | `Close(ctx)` closes `stdin` (a clean EOF, which well-behaved ACP agents treat as shutdown), then waits on the read-loop goroutine and `cmd.Wait()` with `ctx`'s deadline; on timeout, `cmd.Process.Kill()`. The read-loop goroutine's defined way to stop is the `stdout` pipe closing when the process exits or is killed — `Scanner.Scan()` returns false and the goroutine returns. |
| Hang mid-call | Every `Do` call is bounded by the caller's `ctx`. A JSON-RPC call whose response never arrives before `ctx` expires returns `ctx.Err()` to the pack step; the subprocess is not killed on a single call timing out, because a later call (a resume) may still reach it — only `Close` kills it. |
| Death mid-session | `cmd.Wait()` returning is observed by the read-loop goroutine, which then fails every call still waiting on a response with an explicit "agent process exited" error, rather than leaving them blocked forever. |

This is the part of the codebase where context discipline and goroutine ownership matter most
of anywhere so far: one goroutine, one owner, one defined stop condition, and no goroutine that
outlives the adapter it belongs to.

## Failure and negotiation (4.2)

`initialize` runs once, immediately after launch, before any session exists. A version the
adapter does not support, or the absence of a required agent capability (at minimum:
`promptCapabilities` for whatever content types the harness sends; `loadSession` only if a
pack actually asks to resume) fails `acpagent.New` outright — the pack step, and therefore the
whole blueprint run, fails at startup with a named reason, never partway through a `Do` call.
This is the same shape `config.Config.validate()` already uses for "invalid config fails
loudly at boot."

## Testing

No real agent is required for any of 4.1–4.6.

- A **scripted stub** — a small Go test helper that speaks real ACP frames over an
  `io.Pipe`-backed pair standing in for stdin/stdout — drives every adapter test: correct
  framing, `initialize` negotiation (including a version it rejects), `session/new` then
  `session/prompt` then a streamed `tool_call` that the bridge resolves against a fake
  `ports.Registry`, a `session/request_permission` resolved against a fake `ports.Permission`,
  `session/load` replaying recorded history, and a stub that closes its stdout mid-call to
  prove the death-mid-session path.
- The tool-argument flattening (top-level scalar, nested object rejected) is tested directly
  against `json.RawMessage` fixtures, no subprocess involved.
- The permission engine's rule matching and default are tested as pure config-to-decision,
  no I/O.
- **Story 4.7's evidence**, once it runs for real: `claude-agent-acp` installed
  (`npm install -g @agentclientprotocol/claude-agent-acp` — a human runs this, per the
  environment-setup rule; an agent session should not attempt a live global npm install),
  `config.Agent.Command` pointed at it, and a real pack run end to end with permission prompts
  answered on the terminal and the transcript pasted into the increment note. This is a
  config change from the stub tests, not new code.

## Deliberately not in this increment

| Out | Why |
|---|---|
| The `suspend` permission outcome and an out-of-band authorization protocol | Epic 4.6 is the seam; occupying it needs a human-facing surface this codebase does not have until epic 12 |
| Persisting "always allow/deny" as a standing rule | Epic 10.3 promotes a decision into a rule, deliberately, once there is a place for the user to do that promotion |
| Nested/structured tool arguments from an agent | No shipped tool needs them; inventing the shape before a real need would guess |
| `sessionCapabilities.resume` (reconnect without replay) | Not universally implemented across agents; `session/load`'s full replay is the interoperable path, and the one whose guarantees this spec can state precisely |
| MCP servers advertised to the agent via `session/new`'s `mcpServers` field | Atlas's tools reach the agent through the bridge above, not through a second, parallel MCP surface: one path in, not two |
| Gemini CLI or Codex as verified, working ACP peers | Not re-verified here; the config-driven adapter should work against any spec-compliant agent, but only Claude Code's path was checked end to end for this spec |
| A web permission surface | Epic 12. The terminal prompt is the only human-facing surface this epic builds |
