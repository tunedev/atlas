# Epic 13 — The web UI — design

**Supersedes nothing.** This design details Epic 13 of `docs/plans/2026-09-17-roadmap.md` and
sits under `docs/specs/2026-09-17-job-hunt-harness-design.md`. It is written against two
epics that are not built yet: Epic 12's seam (`docs/specs/2026-09-27-epic-surfaces.md`, and
its plan in PR #38), and Epic 10 (roadmap stories only, because no Epic 10 spec has been raised).
Where this design depends on either of them, it says so.

**Goal:** usable by someone who will not open a terminal. The web server is the second driving
surface through Epic 12's seam, not a first implementation. Adding it changes nothing under
`internal/core/`.

## Stories, as the roadmap words them

| Story | Acceptance |
|---|---|
| 13.1 The local server | Serves the UI and the API on localhost only, by default |
| 13.2 Svelte app, embedded in the binary | One file to install; no separate web deploy |
| 13.3 The review surface | See a posting, its verdict, its reasons, and the drafted package |
| 13.4 The decision surface | Approve, override, promote a rule, declare something sent |
| 13.5 When data leaves, it says so | Enabling a hosted `Provider` or `Judge` states plainly what goes where |

## Decisions already taken

| Question | Answer |
|---|---|
| Where the job-hunt screens come from | The UI is generic. A pack ships a view file that declares its screens. The Svelte app contains no job-hunt vocabulary. |
| How consent for a hosted endpoint works | Acknowledged once per endpoint. The acknowledgement is recorded in the git store with the endpoint and the date, it is asked again when the endpoint changes, and a permanent badge shows while one is active. |

## Approaches considered

| | Approach | Verdict |
|---|---|---|
| A | Every screen and every action is a blueprint run through `Runner.Run`. Reads go through two new generic outbound tools. | **Chosen.** It is exactly Epic 12's seam: decode, `Run` with `WithProgress`, encode. There is one path to the record, and no core change. |
| B | The server reads `Docs` and `Index` directly for its lists, and uses blueprints only for writes | Rejected. "What a list is" becomes a rule inside an adapter, and the server gets a second path to the record. It also breaks Epic 12's isolation rule, because an inbound adapter would import `gitdocs` or `sqlindex`. |
| C | The server runs the CLI as a subprocess for each click | Rejected. It fights Epic 12's store lock, costs a process per action, and turns stderr into an API. |

## 13.1 The server

**Invocation.** `atlas -serve` runs the server instead of one pack. It is a branch in `run()`,
beside the pack branch and the agent branch. It takes the same config layers as every other
mode (defaults, then file, then environment, then flags), and it takes Epic 12's
`<Store.Root>/.atlas.lock` for its whole lifetime.

**Package.** `internal/adapters/inbound/web`. Under Epic 12's
`TestInboundAdaptersStayIsolated`, it may import the core and its own subpackages, and nothing
under `outbound/` or a sibling inbound package. For that reason it has its own session token
code rather than reusing `mcpserve.NewToken`: the two are a few lines each, and sharing them
would need a third package that neither surface owns.

**Composition.** `cmd/atlas/main.go` builds the registry once
(`TestBuildRegistryIsCalledOnce`), then hands `web.New` five things:

- a function that returns a fresh `*app.Runner` over that registry;
- the loaded view files;
- the egress table (§13.5);
- the permission rules;
- the web config.

The server builds a runner for each run. Two runs never share a `Runner`, which keeps progress
and tracer callbacks per run.

**One run at a time.** `gitdocs` has no locking, and a decision written while another run
commits would race. The server therefore has one worker, and a run submitted while another
is running queues behind it. A run is bounded by `Web.RunTimeout`, and the browser shows the
queue position. Epic 12's lock serialises processes; this worker serialises runs inside the
one process.

**Transport.** Per Tenet 1, browser-to-platform traffic is RPC-shaped HTTP/JSON through
`connect-go`, and `proto/atlas/web/v1/ui.proto` is the versioned contract. The service is:

| RPC | Shape | Does |
|---|---|---|
| `Views` | unary | The loaded screens, the egress table, and the acknowledgement state |
| `Run` | server stream | Runs one declared screen or action. It streams queue position, then Epic 12's `StepEvent`s, then any permission asks, and ends with the final state or the error. |
| `Answer` | unary | Answers a pending permission ask by its id: allow or deny |
| `Acknowledge` | unary | Records consent for one hosted endpoint (§13.5) |
| `Document` | unary | Returns one record document's bytes and media type, for download |

The final state travels as a JSON string field, because its shape belongs to the pack and not
to the proto. Generated Go and TypeScript are committed, so `go build` needs neither `buf` nor
Node. Protobuf types stop at the `web` package, the same way `*sql.Tx` stops at `gitdocs`.

**Permission asks.** `web` implements `ports.Permission` as an asker, and the composition root
passes it to `app.NewPermissionPolicy` in place of `termprompt` when `-serve` is set. An `ask`
becomes a stream message on the run that caused it, and the run blocks until one of these
happens:

- `Answer` arrives;
- the stream closes;
- `Web.AskTimeout` elapses.

The last two deny. This keeps Epic 12's rule for unattended use: an ask with nobody to answer
it denies, and never hangs.

**Config.** It is added as `WebConfig` and validated at startup:

| Field | Default | Rule |
|---|---|---|
| `Web.Addr` | `127.0.0.1:7878` | The host must parse as a loopback IP. Anything else fails at boot. |
| `Web.Views` | empty | View files to load. The server refuses to start with none. |
| `Web.RunTimeout` | `10m` | Positive |
| `Web.AskTimeout` | `5m` | Positive |

There is no flag, environment variable or setting that binds a non-loopback address. The way
to reach the UI from another machine is an SSH tunnel, and the deployment note documents it.
Binding beyond loopback would need its own design: TLS, real authentication, and a threat model
for a network the user does not control. That design is not this epic.

## 13.2 The embedded Svelte app

- Source lives in `web/`, with Svelte 5 and Vite. Its build output goes to
  `internal/adapters/inbound/web/dist/` and is **committed**. The package embeds it with
  `//go:embed dist`. `go build` and the plane test need no Node.
- CI runs the web build and fails if `dist/` differs from what is committed. That keeps the
  committed bundle honest without making Node a build dependency.
- The app has no router library and no state library. The screens come from `Views`, and the
  URL is `#/<screen>?<param>=<value>`.
- Rendering is a fixed set of generic widgets:

| Widget | Renders | Reads |
|---|---|---|
| `table` | Rows. A row can link to another screen. | A list at a JSON path, the column keys, and an optional `open: <screen>` with the param it binds |
| `fields` | Label and value pairs | An object at a path, and keys |
| `badge` | One short value, emphasised | A path |
| `list` | Strings, one per line | A path |
| `text` | Long text, preformatted and escaped | A path |
| `bins` | A reliability table: one row per bin, showing the `reads` sentence, n, and a bar comparing predicted to observed. A bin whose `observed_rate` is null shows "too few to say (n=…)". | A calibration report at a path |
| `document` | A download link served through `Document` | A record path at a path |

- Everything from the record renders as text. `{@html}` is banned, and a test fails the build
  if it appears in `web/src`. Documents are downloaded with `Content-Disposition: attachment`
  and are never rendered inline, so a hostile posting cannot run script in the UI's origin.

## Views: the pack-declared screen file

A view file sits beside the packs it runs. Paths inside it resolve relative to the file.

```yaml
# packs/job-hunt.ui.yaml
title: Job hunt
discloses:            # what these packs may send to a model endpoint (§13.5)
  - profile summary and CV text
  - posting text
  - drafted cover letter and CV
screens:
  - id: queue
    title: To review
    run: queue.yaml
    show:
      - table: {from: items.rows, columns: [title, company, verdict, when], open: {screen: review, param: {subject_id: subject_id}}}
  - id: review
    title: Posting
    params: [subject_id]
    run: review.yaml
    vars: {subject_id: param.subject_id}
    show:
      - fields:   {from: posting, keys: [title, company, location]}
      - badge:    {from: judgement.verdict}
      - list:     {from: judgement.reasons}
      - list:     {from: judgement.tripped}
      - text:     {from: posting.text}
      - document: {from: package.cv_path}
      - document: {from: package.letter_path}
    actions:
      - label: Approve
        run: decide.yaml
        vars: {subject_id: param.subject_id, choice: const.apply, judgement_path: state.judgement.path, verdict_question: const.verdict}
      - label: Override
        run: decide.yaml
        input:
          - {name: choice, options: [apply, reach, skip]}
          - {name: reason, text: true}
        vars: {subject_id: param.subject_id, choice: input.choice, reason: input.reason, judgement_path: state.judgement.path, verdict_question: const.verdict}
  - id: calibration
    title: How often you were right
    run: judge-calibrate.yaml
    vars: {question: const.verdict, options: const.apply, positive: const.offer, negative: const.rejected, inconclusive: 'const.ghosted,withdrawn,not_applied'}
    show:
      - fields: {from: calibration.pooled, keys: [headline, n, brier]}
      - bins:   {from: calibration.pooled.bins}
      - fields: {from: agreement, keys: [headline]}
```

**Binding sources are closed.** A var's value comes only from:

- `param.<name>`, a declared screen param from the URL;
- `input.<name>`, a declared input from the form;
- `state.<path>`, the screen's last result;
- `const.<value>`, a literal in the view file.

The browser never sends a pack path, a tool name, or an undeclared var. `Run` takes a screen id
or an action index plus the declared values, and the server resolves everything else from the
view file it loaded at startup. This is the load-bearing security rule. The registry includes
`file.read` and `http.request`, so a UI that could run any blueprint would be a local file
reader and a request forger for any page that got a request through.

**The view schema is validated at startup:**

- every `run` resolves to a pack that loads;
- every widget is one of the known set;
- every binding uses a known source;
- every `open` names a screen.

A bad view file fails at boot, never on a click.

**New generic read tools.** Approach A needs reads as tools. Both live in
`internal/adapters/outbound/tools`, beside `docs.put`:

| Tool | With | Returns |
|---|---|---|
| `index.find` | `kind`, `match` (object), `limit` | `{rows: [{path, rev, kind, fields, when}]}` over `ports.Index.Find` |
| `docs.get` | `path`, optional `rev` | `{path, text}`, over `ports.Docs.Get` or `GetAt` |

The queue and review packs (`queue.yaml`, `review.yaml`) are ordinary packs built on these tools
and the existing ones. Both tools are useful from the CLI too. Neither is a surface concern.

**The vocabulary rule extends to `web/`.** `internal/arch/vocabulary_test.go` scans `web/src`
as well as the Go tree, so the job-hunt words live only in `packs/`.

## 13.3 The review surface

It is the `queue` and `review` screens above. What each part depends on:

| Shown | Comes from | Exists today |
|---|---|---|
| The posting | The feed or crawl record, through `docs.get` | Yes (Epics 5 and 8) |
| The verdict, reasons and tripped deal-breakers | The judgement written by `judge.each` | Yes (Epic 7) |
| The drafted package | Epic 10's "one action produces the whole package" (10.1) | **No.** The review pack binds whatever paths Epic 10 records. Until then, the `document` widgets show "not drafted". |

## 13.4 The decision surface

| Action | Pack | Exists today |
|---|---|---|
| Approve | `decide.yaml` with `choice` taken from the verdict | Yes (Epic 6) |
| Override | `decide.yaml` with the user's choice and reason. The decision row gains `agrees` (Epic 7). | Yes |
| Record an outcome | `judge-outcome.yaml` | Yes (Epic 11) |
| Promote a rule | Epic 10's 10.3 pack | **No** |
| Declare sent | Epic 10's 10.4 pack, where the user's declaration starts the clock | **No** |

The UI knows none of these names. When Epic 10 lands, adding its two actions means editing
`job-hunt.ui.yaml` and nothing in Go or Svelte. That is the test of the generic-UI decision.

## The calibration page

The `calibration` screen runs `judge-calibrate.yaml` and `decision.agreement`, both shipped by
Epic 11. It shows:

- the pooled headline, then one `bins` row per bin, with each row's own sentence, for example
  "your 80% judgements came true 55% of the time (n=12)";
- a per-engine report under the pooled one, when there is more than one engine;
- a Brier score shown as "not yet (n<30)" when Epic 11 returns null;
- a bin shown as "too few to say" when its `observed_rate` is null;
- the exclusion counts (pending, zero coverage, inconclusive, unclassified, option mismatch), so
  a small n explains itself.

The page adds no arithmetic. Every number on it is one Epic 11 computed.

## 13.5 When data leaves, it says so

**What the composition root knows.** Epic 12's seam does not describe where a tool sends data,
and it does not need to. `buildRegistry` knows which tools it built over the model provider:

- `model.complete`;
- `judge.ask` and `judge.each`;
- `extract.run`;
- `citations.judge`;
- any other tool whose constructor took the `openaiprov` client.

It also knows which tools are the agent's (`agent.do`). `main.go` builds an **egress table** alongside the
registry, with one row per endpoint:

| Field | Value |
|---|---|
| `endpoint` | `Model.BaseURL` with the path stripped, or `agent:<Agent.Command>` |
| `hosted` | For a model endpoint: true unless the host is `localhost` or resolves to a loopback IP. For an agent: always true, because atlas cannot see where an agent sends what it is given. |
| `tools` | The registry names that send data to it |

A pin next to the registry keeps the table honest: a tool built with the provider client that
is missing from the table fails `TestEgressTableCoversModelTools`.

**What your data is.** Go must not know what a CV is, so the data classes come from the view
file's `discloses:` list. That list is the pack author's plain-language statement of the widest
set of things these packs put in a prompt. It is a declared superset, not a per-run computation.
Deciding per run would mean inspecting prompts, and that is not built.

**The gate.** Before starting a run, the server walks the blueprint's steps. If any step's
tool is in a `hosted` endpoint's `tools`, and that endpoint has no acknowledgement on record,
`Run` refuses with `needs_acknowledgement` and the endpoint. The browser then shows, in full:

> This will send **profile summary and CV text, posting text, drafted cover letter and CV** to
> **https://api.example.com**, which is not on this machine. Nothing is sent until you agree.
> [Send and remember for this endpoint] [Cancel]

`Acknowledge` records `{endpoint, discloses, when}` under the reserved record path
`atlas/egress/<endpoint hash>.json`. It is written by a blueprint the `web` package builds
itself, one `docs.put` step through `Runner.Run`, so it is committed history like any other
decision. The acknowledgement is keyed by the exact endpoint string and the `discloses` list:

- changing `Model.BaseURL` asks again;
- adding a class to `discloses` asks again;
- pointing at a local engine never asks.

**The badge.** While any hosted endpoint is configured, every screen carries a fixed header:
"Data leaves this machine: <endpoint>". It cannot be dismissed, and clicking it shows the
egress table. When no endpoint is hosted, the header reads "Everything stays on this machine".

**The CLI is unchanged.** The gate is a web concern. A user running a pack from the terminal
configured the endpoint themselves, in the same session. Whether the CLI should gate as well is
recorded under Not built.

## What is never exposed

Concretely: this machine holds a real CV, real salary expectations and a real employment
history.

| Never | How |
|---|---|
| Reachable from another machine | The loopback-only bind, validated at boot, with no override (§13.1) |
| Reachable from another local user or process without the token | Each start prints `http://127.0.0.1:7878/#token=<32 bytes from crypto/rand>` once to stderr. The first load exchanges it for an `HttpOnly; SameSite=Strict; Path=/` session cookie, and every RPC checks the cookie in constant time. The token is never logged again, and a restart invalidates it. The token rides in the fragment, which browsers do not send, so it never lands in a request line or a proxy log. |
| Reachable from a web page the user visits | Three checks. **DNS rebinding:** a request whose `Host` is not the bound loopback host and port is refused. **Cross-site writes:** a request whose `Origin` is absent or foreign is refused. **Reading responses:** no CORS headers are sent, ever. Every response carries `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`. |
| Any file outside the record, or any tool not declared by a view | The closed binding sources (§Views). `Document` serves record paths only, through `docs.get`, never a filesystem path. |
| The model API key | `Model.APIKey` never appears in `Views`, the egress table, any stream message, or any log. `TestNoResponseCarriesTheAPIKey` sets a sentinel key and scans every RPC's output for it. |
| The CV file itself | Already true since Epic 6: the record holds the extracted profile, not the original upload. |
| Salary, profile and CV text sent anywhere without the user saying so | They leave the machine only through a hosted endpoint, and only after §13.5's acknowledgement. They reach a local engine without asking, because a local engine is not "leaving". |

Everything else in the record is served to the one authenticated local session, because
showing it to its owner is the product.

## Findings about Epic 12's seam

The brief asked for these to be reported, not designed around.

1. **Progress is per step, not per item.** `StepEvent` fires around a whole step, and
   `judge.each` over 200 postings is one step. The UI can show "judging…", but not "37 of 200".
   Showing the second would need a within-step progress channel from tools to the runner, which
   is a core change. This design shows per-step progress only, and records the gap.
2. **While `-serve` is running, the CLI cannot use the same store.** Epic 12's lock is
   per-process by design. It is correct, but it is visible to the user, so the startup line and
   the deployment note both say "stop the server to use the CLI on this store".
3. **The seam is otherwise sufficient.** Both the web permission asker and the egress table plug
   in at the composition root. The reads are adapter tools. Nothing in this design edits a file
   under `internal/core/`. That confirms Epic 12's story 12.6 by a second, independent design.

## Testing

These are the tests that would catch this epic broken:

| Test | Catches |
|---|---|
| `TestServeRefusesNonLoopbackAddr` | Config accepting `0.0.0.0`, `::`, or a LAN IP |
| `TestRejectsForeignHost`, `TestRejectsForeignOrigin`, `TestRejectsMissingSession` | Rebinding, CSRF, and a missing token. Each is exercised over real HTTP against `httptest`. |
| `TestRunRefusesUndeclaredPackOrVar` | A browser naming a pack, a tool, or a var the view does not declare |
| `TestViewFileValidatedAtStartup` | A bad widget, binding or `run` path failing at boot rather than on a click |
| `TestAskDeniesWhenStreamCloses`, `TestAskDeniesOnTimeout` | A permission ask hanging a run forever |
| `TestRunsAreSerialised` | Two concurrent `Run`s interleaving writes to the store |
| `TestHostedEndpointNeedsAcknowledgement` | A run reaching a hosted model before consent; a changed endpoint or `discloses` list not asking again; a loopback engine asking at all |
| `TestEgressTableCoversModelTools` | A new model-backed tool missing from the table |
| `TestNoResponseCarriesTheAPIKey` | A key leaking through any RPC |
| `TestNoRawHTMLInWebSource`, vocabulary scan over `web/src` | Script injection, and job words in the generic UI |
| Epic 12's `TestInboundAdaptersStayIsolated` | `web` importing an outbound adapter or `mcpserve` |
| CI: web build matches committed `dist/` | A stale embedded bundle |
| End to end: `atlas -serve` against a fixture store with the test engine, driving `Views`, then `Run` of `review`, then `Run` of Approve through the Connect JSON protocol | The whole path from the view, through the blueprint and the record, to the decision row, with `agrees` set |

No browser automation. The Svelte widgets are small, and the contract they render is tested at
the RPC.

## Not built

| Not built | Why |
|---|---|
| Any non-loopback bind, TLS, or accounts | This needs its own threat model. An SSH tunnel covers remote use today. |
| Within-step progress | A core change (Finding 1) |
| Per-run disclosure, computed from the actual prompt | The `discloses` list is a declared superset, and inspecting prompts is a separate design |
| The same consent gate on the CLI | The terminal user configured the endpoint in the same session. Revisit if packs start being shared. |
| Editing packs, view files or config from the UI | The UI runs what is declared. It does not author. |
| Concurrent runs | `gitdocs` is unlocked, and one person clicks one thing at a time |
| A router, a state library, or a component kit in the Svelte app | The widget set is small enough without one |
| Live push of record changes made elsewhere | The CLI cannot run while `-serve` holds the lock, so nothing else writes |
| Epic 10's promote-rule and declare-sent actions | Epic 10 is not specified yet. They arrive as view-file edits when it lands. |
