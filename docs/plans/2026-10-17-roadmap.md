# Atlas roadmap — the product and the factory

Atlas is a harness for domain-specific agents. Its first product is job search: find the
latest relevant postings, keep watching for more like them, and have every application
drafted before you open it. Atlas is also the first product built end to end by the
software factory (foundry and vouch), and the factory is built to the Agentic Coding
Paradigm (ACP).

Each stage below gets its own spec, plan and implementation, in the owning repo. A stage
starts when the previous stage's gate is met.

This roadmap follows `2026-09-17-roadmap.md`, whose epics 0 to 13 have landed. Stage 5
says how the search contracts spec's sessions map onto it; its session E is stages 2 and 3.

## The product

### Components

Each component stands alone and is composed into atlas by configuration.

| Component | Repo | Role in atlas |
|---|---|---|
| atlas | `tunedev/atlas` | Harness, packs, web UI, the record |
| nerve | `tunedev/nerve` | Storage and memory: hybrid (vector and keyword) search, sessions, durable memory |
| cana | `tunedev/cana` | Document conversion and extraction |
| feed | `tunedev/feed` | Job sources: ATS board APIs and rendered careers pages. Atlas reads it through `feedsource` |

### The MVP demo

1. Search the latest jobs by keyword or meaning across every source, newest first, in a
   glassdollar.com-style UI.
2. Add a source. Sources that need a login use browser tools; credentials never enter a
   model's context.
3. Open a job. Its details and apply link are the employer's own posting, even when it
   was found on an aggregator.
4. Pick the jobs that fit. A background run keeps searching every source for similar
   jobs and puts them on a review board: to review, apply, applied.
5. Move a job to apply. An agent reads that application's questions and documents and
   drafts every answer from your background, citing your own text. Nothing is submitted.
6. Mark it applied. The job and its drafts go to nerve as memory for what comes after.

After the MVP: interview preparation, follow-ups and outcome tracking, built on the
memory step 6 writes.

| Environment | Where | Purpose |
|---|---|---|
| qa1 | This workstation | Always-on home deployment; per-PR previews; the evidence environment |
| hosted | A free cloud tier | The reduced stack: app and Postgres. Never billed |

There is one user. Stage 2 adds a `make preflight` that names every missing requirement,
after which anyone who meets them can bring atlas up on their own machine or

### Local-first, amended

The single binary over the git record stays the default and keeps working offline, on a
laptop, for free. The job data pipeline (stage 4) is how atlas runs when deployed, on qa1
and on the hosted tier; it is not required to run atlas. The hosted tier is the user's own
free-tier deployment, never a service run for others. The global constraint in
`2026-09-17-roadmap.md` ("no server we operate") changes to this in stage 4's spec, with
`README.md` updated in the same change.

## The factory

Agents ship; the human decides what the product is, and merges. Two references shape the
factory:

- **ACP** (*Code Is Not the Product: The Agentic Coding Paradigm*). Changes are understood
  as shifts in meaning, scored by risk, and approved by evidence. Five phases, each gated:
  semantic change reports; the map as a service; scoped tokens and evidence-based
  escalation; risk lanes and a verifying judge; disposable environments, the production
  loop and contract-level scopes.
- **Kody** (Kent C. Dodds). Three layers of trust: agents make good PRs (decisions,
  primitives, a control CLI, a system recap in every PR), mistakes are caught before
  production (a deterministic ship process, AI reviewers, previews), and production
  limits the blast radius (feature flags with success metrics, tested restore). Signal
  sources feed work in: friction, dogfooding, errors, scheduled cleanup.

Where they differ, atlas takes this side:

| Question | Choice |
|---|---|
| Who writes the system recap | The agent states intent; vouch derives the recap from the code and flags a mismatch |
| Who reviews | A model from a different vendor than the author's |
| Who merges | The human, until risk lanes earn auto-merge for a lane |

## Work items

Every stage is a set of work items named `<component>/<item>`. The component is the repo
that owns the change: `atlas`, `nerve`, `cana`, `feed`, `infra`, `vouch` or `foundry`. Each
item becomes one issue in its repo, and foundry works the issues of different repos in
parallel. An item lists what it needs; an item with no needs starts with its stage.

A stage's spec sets each gate's numbers where this roadmap leaves them open.

### 4. The job data pipeline

Jobs stop arriving through a scheduled GitHub Action that commits to a git repo. Feed
becomes the set of source pollers: each source is called at its own cadence with
conditional requests, change detection and a breaker per source, and a posting that
leaves its source is marked closed. Deployed, Postgres is the system of record and changes
leave through a transactional outbox to RabbitMQ, where idempotent consumers enrich,
resolve the employer's posting, embed and index through nerve, and match saved searches.
Replay reads Postgres, never the broker. Offline, the single binary runs the same pollers
into its own record and indexes locally.

| Item | Delivers | Needs |
|---|---|---|
| `feed/pollers` | Feed's fetchers as pollers with cadence, conditional requests, change detection, breakers and closed-posting detection; the scheduled Action and git store retired | |
| `atlas/ingest` | Postings into Postgres with an outbox, and into the local record offline | `feed/pollers` |
| `infra/pipeline` | Postgres and RabbitMQ for atlas on qa1, with backups and a scheduled restore test | `infra/qa1` |
| `atlas/consumers` | Enrich, resolve and match consumers; new matches pushed to the review board | `atlas/ingest`, `infra/pipeline` |
| `nerve/postings-index` | Hybrid index of postings, rebuildable from Postgres | `atlas/ingest` |
| `infra/freshness-slo` | Posted-at-source to searchable, p95, on the Grafana board | `atlas/consumers` |

Gate: the freshness target holds on qa1 for seven days; replay rebuilds identical
indices; a failing source or broker loses nothing; a restore test passes.

### 5. The MVP slices

The search contracts spec (`docs/specs/2026-10-12-search-contracts-design.md`) supplies
the first slices: session B's enrich, SQLite FTS index and match are the offline default
path, sessions C and D are slice 1 and slice 5, and session A's de-duplication is slice 3.
Semantic search is out of that spec's scope, so slice 2 amends it.

Freshness is a default search criterion: every saved and ad hoc search starts with a
posted-within window and ranks newer postings first, and every result shows its age.

| Item | Delivers | Needs |
|---|---|---|
| `atlas/search` | Slice 1: keyword search with the freshness default and the glassdollar-style UI | |
| `nerve/semantic` | Slice 2: semantic queries over postings | `nerve/postings-index` |
| `atlas/semantic` | Slice 2: semantic and keyword results fused in one search | `atlas/search`, `nerve/semantic` |
| `atlas/canonical` | Slice 3: the employer's posting as the job's record; duplicates merged | `atlas/consumers` |
| `atlas/watch` | Slice 4: saved searches seeded from picked jobs, run in the background, onto a review board (to review, apply, applied) | `atlas/search` |
| `atlas/drafts` | Slice 5: on apply, every application question and document drafted from the profile, citing its text | `atlas/canonical` |
| `cana/forms` | Slice 5: extraction of an application's questions and required documents | |
| `nerve/applied` | Slice 6: applied jobs and their drafts kept as memory | |
| `atlas/applied` | Slice 6: marking a job applied writes it to nerve | `atlas/watch`, `nerve/applied` |
| `atlas/login-sources` | Slice 7: sources behind a login. Starts with a decision record reversing the crawler's conduct rule (epic 8.6, enforced by `TestTheCrawlerHasNowhereToHoldACredential`). The crawler stays credential-free; logins live in a separate browser-tools surface that keeps session state outside the model's context | |

Experiments ship behind feature flags that name a success metric.

Gate: the demo runs end to end on a clean machine by following the README.

| Item | Delivers |
|---|---|
| `foundry/sources` | Work from dogfooding agents, errors in telemetry, scheduled docs and test gardening, a weekly sweep for unused code |

map answers match reality on a sampled set; escalations are rare and no write lands out of
scope; audits of auto-approved changes stay under a miss rate the phase 4 spec sets.
