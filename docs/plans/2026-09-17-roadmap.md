# Atlas roadmap — epics and stories

**Spec:** `docs/specs/2026-09-17-job-hunt-harness-design.md`

Thirteen increments. Each is an epic; each epic gets its own task-by-task implementation
plan **when its predecessor lands**, not before — increment 3 cannot be specified in detail
until increment 2 says what a `Provider` actually returns.

Only increment 0 has a detailed plan today: `2026-09-17-increment-0-tracer.md`.

## Global constraints

Bind every epic.

- Go 1.27. Module `github.com/tunedev/atlas`. Go end to end.
- Hexagonal: `internal/core/{domain,ports,app}`, `internal/adapters/{inbound,outbound}`,
  `cmd/atlas/main.go` the only file knowing every concrete type.
- **Nothing in the Go tree knows what a job posting is.** Use-case vocabulary lives in
  `packs/` and nowhere else. `internal/arch/vocabulary_test.go` enforces it.
- No core package imports an adapter or a driver. `internal/core/...` compiles in neither
  `net/http` nor `crypto/tls`. `internal/arch/arch_test.go` enforces both.
- A port exists only where a second implementation is nameable.
- `ctx context.Context` first parameter of every blocking or remote call. Never stored in a
  struct. Every remote call has a timeout; the default is not "no timeout". Every response
  body is bounded.
- Nothing operationally interesting is hardcoded past `config.defaults()`.
- Local-first: no account, no server we operate, nothing about a user leaves their machine
  unchosen. A month bills nothing.
- No emojis in code, logs or output. Comments describe current behaviour only.
- Tests assert behaviour. A test that cannot fail is a defect.
- Every increment ends with a note in `docs/notes/`.

## Epic 1 — `Docs` and `Index`

**Why:** the record has to exist before anything worth recording does. Git is the system of
record; SQLite and DuckDB are derived.

| Story | Acceptance |
|---|---|
| 1.1 `Docs` port over git | A document is written, committed, and read back by path and by revision |
| 1.2 History is queryable as history | The revisions of one document are listable, and any prior revision is retrievable |
| 1.3 `Index` port, SQLite adapter | Documents are findable by field without reading the repository |
| 1.4 DuckDB adapter | The same port, backed by DuckDB, for queries that scan history |
| 1.5 Rebuild from the record | Deleting both indices and rebuilding them from git loses nothing. **Asserted by test, not by claim** |
| 1.6 One binary still | `go build` produces a self-contained binary; CI builds per platform because DuckDB needs cgo |

## Epic 2 — `Provider`

**Why:** the scorer and the doer both need a model, and which model must be a config line.

| Story | Acceptance |
|---|---|
| 2.1 `Provider` port in the core's vocabulary | Takes a prompt, returns a completion. No vendor name in the signature |
| 2.2 OpenAI-compatible adapter | One adapter serves vLLM, Ollama and a hosted key; only the base URL differs |
| 2.3 vLLM running locally | Documented bring-up on 8 GB of VRAM, with the quantisation and context length that actually fit |
| 2.4 Ordered provider chain | A failing provider degrades to the next; a breaker stops hammering one that is down |
| 2.5 `model.complete` moves behind the port | The tool stops knowing which vendor answered; `Completion` records which did |
| 2.6 Cost and latency are observable | Tokens and duration land on the span that caused them |

## Epic 3 — `Judge`, locally

**Why:** judgement must be a value, not a paragraph. This is the epic the product's quality
rests on.

| Story | Acceptance |
|---|---|
| 3.1 The three question types | `noul`, `choice` and `score` are domain types with the answer shapes the spec names |
| 3.2 Speculative fan-out in one call | Many typed questions, one round trip, answers keyed by question id |
| 3.3 Shape by constrained decoding | A `choice` can only return an allowed option. Asserted against a model that is told to misbehave |
| 3.4 Probability by logprobs | A `noul` is derived from token logprobs, not from asking the model for a number |
| 3.5 Every judgement is recorded for later checking | The question, the answer, the probability and the eventual outcome slot are persisted together. **Without this, epic 7 inherits confident nonsense** |
| 3.6 Offline | The whole epic's tests pass with no network |

## Epic 4 — `Agent`, over ACP

**Why:** the doer is an agent the user already pays for. ACP already specifies tool calls,
permissions and session resume.

| Story | Acceptance |
|---|---|
| 4.1 JSON-RPC over stdio | A subprocess is launched, framed messages go both ways, and it shuts down cleanly |
| 4.2 Initialise and negotiate | Version and capabilities are agreed; an unsupported peer fails loudly at startup |
| 4.3 Session lifecycle | New, prompt, streamed updates, close |
| 4.4 Tool calls from the agent reach our registry | An agent asking for a tool gets ours, through the existing `ports.Tool` |
| 4.5 Permission requests surface | The agent asking permission reaches the allow/ask/deny engine rather than being auto-approved |
| 4.6 Session resume | A session resumes where it stopped. This is the A2H seam, and ACP already defines it |
| 4.7 A real agent completes a real pack | Gemini CLI, end to end, evidence pasted |

## Epic 5 — The postings feed

**Why:** unattended discovery without a backend.

| Story | Acceptance |
|---|---|
| 5.1 A normalised posting schema | One shape, whatever the source. Versioned, because consumers pin to it |
| 5.2 Fetchers for the structured boards | Greenhouse, Lever, Ashby, Workable, RemoteOK |
| 5.3 The scheduled Action | Crawls, normalises, commits to a public repository. Free on standard runners |
| 5.4 Rendered sources, in the Action | Rod fetches a JS-rendered careers page and yields normalised postings. Runs in CI, where a browser is already present and free |
| 5.5 A page needing JS says so | An HTTP-only fetch of a rendered page reports "needs rendering", never zero results |
| 5.6 The app pulls the feed | `Source` implementation over a git remote |
| 5.7 A stale feed is noticed, not trusted | The app reports feed age and warns when the schedule has stopped |
| 5.8 No user data reaches it, ever | Asserted: the feed repository contains postings and nothing else |

## Epic 6 — Profile

**Why:** fit judgement is meaningless without knowing who is being judged.

| Story | Acceptance |
|---|---|
| 6.1 CV ingest into structured history | A CV becomes roles, dates and claims the user can correct |
| 6.2 Corrections are the record | An edit is a commit; the original is still retrievable |
| 6.3 Preferences and deal-breakers | Goals, salary floor, location, and the things that are a hard no |
| 6.4 The evidence corpus | Past letters, write-ups and reviews that tailoring may quote |
| 6.5 The decision log | Every apply and skip is a labelled example. Revealed preferences outlast stated ones |
| 6.6 Purge | A document removed from the profile is gone from history too, not only from HEAD. Needs its own design: it breaks `Docs`'s no-overwrite invariant |
| 6.7 Attribution check | Before Epic 7 consumes history, an entry whose fields disagree with its own quote, or an entry the source states but extraction dropped, is flagged — a grounded quote alone does not make an entry correct |

## Epic 7 — Fit judgement

**Why:** this is where the numbers game stops being a numbers game. Adds no new unknown —
it is epic 3 pointed at epic 6.

| Story | Acceptance |
|---|---|
| 7.1 Apply, stretch or skip, with reasons | A verdict a human can read and disagree with |
| 7.2 A tripped deal-breaker is named | Not "not a fit" but which rule fired |
| 7.3 Disagreement is recorded | The user overriding a verdict is training data, not a lost click |
| 7.4 Scoring a board is one batch | Two hundred postings scored without two hundred round trips |

## Epic 8 — Local crawling

**Why:** the roles worth having are often the ones with no API.

| Story | Acceptance |
|---|---|
| 8.1 `Source` over Colly, HTTP only | A static careers page yields normalised postings. Colly does not run JavaScript, and this story does not pretend otherwise |
| 8.1a Rendering is opt-in and uses an existing browser | Off by default. When enabled, `launcher.LookPath()` finds the user's own Chrome; the app never downloads one |
| 8.2 Politeness is enforced in code | Per-host rate limit, `robots.txt`, identified user agent. Not documented — enforced |
| 8.3 Incremental recrawl | A rerun is cheap; unchanged pages are not refetched |
| 8.4 Extraction staleness is loud | A page whose shape changed reports zero-with-an-error, never zero-silently |
| 8.5 Deduplication across sources | The same role from a board, an aggregator and a careers page counts once |
| 8.6 Never authenticated | Asserted: the crawler holds no credential and logs into nothing |

## Epic 9 — Tailoring

**Why:** the half of the trade that volume normally destroys.

| Story | Acceptance |
|---|---|
| 9.1 A CV variant per role | Drawn from the structured history, ordered for this posting |
| 9.2 A letter that cites evidence | Every claim traces to a document in the corpus |
| 9.3 An unsupported claim is a visible gap | Shown as missing, never written as fact. **This is the anti-hallucination requirement** |
| 9.4 Answers to the posting's own questions | Drafted from the same evidence |
| 9.5 The output format decision | Structured text, or a PDF toolchain. Decided here, with the reason recorded |

## Epic 10 — The apply loop

**Why:** drafting is the product. Submitting is refused, and the refusal has a written
reversal condition.

| Story | Acceptance |
|---|---|
| 10.1 One action produces the whole package | CV variant, letter, answers, submission URL and instructions |
| 10.2 allow / ask / deny over postings | Default ask; deny beats allow; a deal-breaker is always deny |
| 10.3 A repeated decision can become a rule | Promoted deliberately by the user, never inferred silently |
| 10.4 Drafted and sent are distinct states | The platform cannot see the boundary, so the user declares it. That declaration starts the clock |

## Epic 11 — Tracking

**Why:** the corpus only becomes useful once outcomes are attached to decisions.

| Story | Acceptance |

| 11.1 Pipeline state per application | Where each one is, and for how long |
| 11.2 What has gone quiet | Staleness measured from the declared send |
| 11.3 Outcomes recorded through to offer or rejection | The label epic 3's recorded judgements were waiting for |

## Epic 12 — The web UI

**Why:** usable by someone who will not open a terminal. Last, deliberately: clients come

| Story | Acceptance |
|---|---|
| 12.1 The local server | Serves the UI and the API on localhost only, by default |
| 12.2 Svelte app, embedded in the binary | One file to install; no separate web deploy |
| 12.3 The review surface | See a posting, its verdict, its reasons, and the drafted package |

## Sequencing

0 first and alone. Then 1 (the record) and 2 (the model) in either order; 3 needs 2. 4 is
independent of 3 and can run in parallel with it. 5 is independent of everything. 6 needs 1.
7 needs 3 and 6. 8 needs 5's schema. 9 needs 6. 10 needs 9. 11 needs 10, and closes the loop
back to 3.5. 12 needs something worth looking at, which is 10.

The one hard ordering constraint that is easy to get wrong: **3.5 must land with epic 3, not
later.** It records the judgement alongside a slot for the outcome. Adding it after epic 7 is
built means every judgement made before then is unverifiable forever.
