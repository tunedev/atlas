# Epic 5: the job-hunt pack reads the feed

## What the pattern was

`ports.Source` answers two questions only — `Pull` (everything present) and `LastRefreshed`
(how fresh) — and returns opaque `Item{ID, Body, When}`. The core never parses `Body`; a pack
narrows it by path, the same way it already narrows any tool's result. `feedsource.Source`
implements the port by keeping one bare cache (`git.PlainInit(path, true)`), fetching the
configured ref at depth one into `refs/atlas/pinned`, peeling an annotated tag if the ref is one,
and reading every `.json` file out of the pinned commit's tree. `source.pull` sits in front of
the port as the tool a pack actually calls: it decodes each item's bytes into a document, applies
an optional `prefix` (a directory boundary) and `match` (`field=value`), and reports
`_meta.age_hours`/`stale` alongside the kept items. Repointing `packs/job-hunt.yaml` at this
stack needed a five-line `with:` block and three field renames (`company_name` to `company`,
`content` to `description_text`, `location.name` to `location`) — the pack changed, nothing under
`internal/core` did.

Run against a local clone of `feed`, crawled live and committed once:

```
role.id=greenhouse/gitlab/8396674002 role.status=open role.company=GitLab
role.title="Manager, Solutions Architects - San Francisco "
judged: stretch=no(p=0.75) seniority=senior(p=0.64) focus=data(p=1)
verdict: decision=skip reasons=["The role is for a Solutions Architect and Manager position
  in San Francisco, which does not align with the candidate's experience as a Backend Engineer."]
```

`judged` and `verdict` both ran on `description_text`, confirming the field rename reaches the
model, not just the template.

## What the bare depth-one cache proved

`ls "$tmp/cache"` after a real `Pull` is exactly `HEAD config objects refs shallow` — no working
tree, no index, the shape a bare depth-one clone is supposed to have. `git -C "$tmp/cache"
rev-list --all | wc -l` is `1`: the cache never accumulates history, it holds only the current
tip, however many times `Pull` runs. A second `Pull` (the `hn-summary` run and the stale-config
run that followed) reused the same cache directory without error, so "a cache already tracking a
different remote fails loudly" (R12) was exercised on the happy path too — same remote, same
path, no fetch complaint. `source.pull` at `-feed-stale-after 1s` reliably logged
`level=WARN msg="source is stale" age=1m0s stale_after=1s last_refreshed=2026-09-24T18:38:45Z`
on the very next run, seconds after a fresh pull — proving the staleness check reads the pinned
commit's real time, not a cached "just fetched" flag.

## The pack diff

`vars.board_api` is gone; `vars.board` stays. The `role` step's tool changed from `http.request`
against Greenhouse's public API to `source.pull` against the feed, with `prefix:
"postings/greenhouse/{{ .vars.board }}"` and `match: status=open` doing the narrowing the old URL
template used to do with a board slug in the path. Every later step's three field references
were renamed to match the feed's schema (`schema/v1.md` in `feed`); `id` and `title` were already
the same name in both shapes and needed no change. `packs/hn-summary.yaml` runs unmodified and
never touches `-feed-*` flags, `feedsource`, or `source.pull` — it has no `role`-shaped step, so
nothing about this task's changes reaches it, confirmed by running it last and watching it return
a Hacker News item with no feed cache created.

## What a live board did that no fixture predicted

Nothing on atlas's side. The pack's three renamed fields (`company`, `description_text`,
`location`) round-tripped through the real GitLab posting exactly as `schema/v1.md` describes
them, and `judge.ask`/`model.complete` produced ordinary distributions and a well-formed verdict
JSON from real, much longer prose than any fixture carries. `feed`'s own note
(`~/forge/feed/docs/notes/2026-09-24-epic-5.md`) already records the crawl-side surprise (693
postings across six boards, `lever/palantir` at 319 the largest by far); nothing about running
`atlas` against that data surfaced a second one.

## What I still do not understand

Q1 stays the one unverified assumption in the epic, unchanged by this task: whether a
scheduled workflow that commits every six hours keeps GitHub from treating `feed` as idle and
disabling the schedule. This task never touched the live GitHub Action — the public feed has no
PR-merged data yet, so the whole path above was proven against a local clone crawled by hand. The
ruling's fallback (atlas's staleness check, exercised above, plus `gh workflow enable crawl.yml
-R tunedev/feed`) is written and ready; verifying the schedule itself survives sixty idle days is
Task 13's Step 5, deferred until the owner merges `tunedev/feed#1`.
