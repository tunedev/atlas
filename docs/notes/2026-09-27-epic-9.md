# Epic 9: tailoring, and what a checked letter actually says

## What the pattern was

**Cite by id, check in code, render only what survived.** The model never types a fact about
the candidate. `text.spans` numbers the record's lines, the model answers with span numbers,
and code does the rest: `span.resolve` swaps each id for its verbatim text (an invented or
out-of-range id becomes an empty quote), `quote.ground` proves the quote exists,
`citations.judge` asks one yes/no relevance question per (claim, span) pair, and
`claims.settle` turns anything uncited or rejected into a gap. Every object with a `text` key
is a statement: with no citations list, or only whitespace for text, it is a gap, and settle
always sets its gap flag, so a model-supplied `gap:false` never survives.

**Three documents, two audiences.** `cv.pdf` and `letter.pdf` are sendable: they carry only
kept content. `review.pdf` is for the person sending them: requirements the record does not
show, letter and answer sentences removed for lack of evidence, questions the record does not
answer, and the dropped counts. `render.run` reads each PDF back and fails, publishing nothing,
if a kept statement is missing (`expect`) or if any gap text from `claims.settle`'s
`gaps_text` is printed outside kept content (`absent`): a gap word that also occurs inside a
kept bullet is not a printed gap. The review sheet must print every gap text.

**What is asked comes from the source, not from the model.** The asked step extracts every
requirement as a verbatim quote, grounded against the posting, and `items.cite` builds one
claim per requirement. The questions need no model: `text.lines` makes one grounded item per
line of the questions var, and `items.gather` gives each question the sentences written for it;
a question nothing answers gets one empty sentence, which settles as a gap. An answer sentence
is judged with its question as part of the subject, so it is checked as an answer. A
requirement or question the model cannot support becomes a gap instead of vanishing.
Requirements that were not verbatim in the posting are dropped and counted in
`tailored.json`'s index fields and on the review sheet.

**None of it knows what a CV is.** The Go tree speaks of spans, citations, claims and gaps.
The pack and its templates own the vocabulary.

## The empty letter: root cause and fix

Task 8's live runs returned `{"letter":[],"answers":[]}` on both qwen2.5-coder:7b and
mistral-small3.2. Plan ruling R10 predicted a cause: `extract.run` always sends the
Extractor's fixed "extract only what the text states" system message, which might forbid
writing new sentences.

**R10 tested and rejected.** A logging proxy between atlas and Ollama 0.23.0 captured the
exact letter request. Replayed straight to `/v1/chat/completions` (json_schema strict,
temperature 0), letter sentences per run:

| Model | (a) extractor system message | (b) "write a short cited letter" system message |
|---|---|---|
| qwen2.5-coder:7b | 0, 0, 0 | 0, 0, 0 |
| mistral-small3.2 | 0, 0, 0 | 0, 6, 6 (a fourth call: 3) |

On the default model both are empty, so the system message is not the cause.

**Varying one thing at a time (qwen, letter request):**

| Variant | Reply |
|---|---|
| no system message | `{"answers":[],"letter":[ ]}` |
| strict off | `{"answers":[],"letter":[ ]}` |
| schema with only the letter field | `{"letter":[ ]}` |
| `json_object` instead of a schema | `{"letter":"I am writing to apply..."}`, a string |
| no response format at all | a six-sentence letter, citing "(Evidence Span [0])" in prose |

The model writes a letter whenever it is free to. It just does not write it in the schema's
shape. Prompt size is not the cause: 242 prompt tokens against a 4096 context.

**Root cause: the schema never reaches the model.** Ollama turns `response_format` into a
decoding grammar and never puts the schema in the prompt. At `[`, the model's preferred next
token (a string for the letter, an integer for bullets) is illegal where the schema wants an
object, and the cheapest legal continuation is `]`. Ollama's structured-outputs doc says so
itself: "It is ideal to also pass the JSON schema as a string in the prompt to ground the
model's response."

**Confirmed.** The captured requests were replayed with one change, the schema appended to the
user message. The extractor system message stayed as it was. Items per run, qwen, 3 runs each:

| Step | Schema not in prompt | Schema in prompt |
|---|---|---|
| requirement citations | 0, 0, 0 | 4, 4, 4 |
| bullets | 0, 0, 0 | 2, 2, 2 |
| letter | 0, 0, 0 | 3, 3, 3 |
| letter, mistral-small3.2 | 0, 0, 0 | 3, 3, 3 |

So the whole tailoring was empty on the default model, not only the letter. Task 8's CV came
from mistral, and it called qwen's empty bullets "a model-capability gap". It was not one.

**Fix, at the source.** `app.Extractor.Extract` appends "Reply with JSON matching this schema:"
and the schema to the user message, and still sets `Prompt.Schema` for the grammar. That one
change covers every `extract.run` caller. It is not in `openaiprov`, because that would also
change the Judge's prompts and move its measured probabilities. The extract-only system
message is unchanged. The unit test asserts the schema appears verbatim in the user message
and that `Prompt.Schema` is still set, and two mutations prove it: dropping the append, and
dropping `Schema`.

## The fabricated run

A made-up keeper, Maren Tollow, with two made-up employers and nine bullets, was compiled to
PDF with `typst` and ingested with `packs/profile-ingest.yaml` into a throwaway store. The
posting asks for six things. The record supports three (maritime logs, radio coordination
with the coastguard, planning berth schedules) and not the other three (a harbour pilot licence,
five years of tall ship sailing, a first aid at sea certificate). The questions var holds two
questions, one per line: one the record supports (radio coordination with the coastguard in
bad weather) and one it does not (a harbour pilot licence). `packs/tailor.yaml` ran on
qwen2.5-coder:7b with `ATLAS_RENDER_TYPST=typst`, in 27 seconds.

### cv.pdf (pdftotext -layout)

```
Experience
Harbour Master’s Assistant, Gull Bay Harbour Trust
2021 – present

Lighthouse Keeper, Point Rook Light
2016 – 2021

Selected work
• Wrote the monthly tide and weather notice posted at the harbour office.
• Kept the lighthouse log at Point Rook for five years, recording every passing ship by name and hour.
• Lighthouse Keeper, Point Rook Light, 2016 – 2021
• Scheduled berths for up to forty fishing vessels a week using the Trust’s booking ledger.
• Coordinated with the coastguard by radio during storms to warn vessels off the reef.
• Inspected mooring chains every quarter and logged wear against the Trust’s replacement schedule.
• Led the harbour’s oil spill drill twice a year with the fire service.
```

### letter.pdf (pdftotext -layout)

```
I have over five years of experience as a Harbour Master’s Assistant at Gull Bay Harbour Trust. During
this time, I coordinated with the coastguard by radio during storms to warn vessels off the reef and
scheduled berths for up to forty fishing vessels a week using the Trust's booking ledger. I inspected
mooring chains every quarter and logged wear against the Trust’s replacement schedule, ensuring the
safety of the harbor. I led the harbour's oil spill drill twice a year with the fire service, demonstrating my
ability to plan and execute emergency procedures. I wrote the monthly tide and weather notice posted
at the harbour office, keeping accurate records of maritime information.

Answers to the questions asked
Can you coordinate with the coastguard by radio in bad weather?
Coordinated with the coastguard by radio during storms to warn vessels off the reef.
```

### review.pdf (pdftotext -layout)

```
Review before sending
Requirements not shown by the record
• experience keeping accurate maritime logs
• experience planning berth schedules
• a harbour pilot licence
• five years of tall ship sailing
• a first aid at sea certificate

Questions not answered by the record
• Do you hold a harbour pilot licence?

Counts
• Requirements dropped as not verbatim in the posting: 0
• Bullets dropped for lack of evidence: 0
```

No gap text appears in `cv.pdf` or `letter.pdf`: every `gaps_text` entry and the unanswered
question were checked against both PDFs' extracted text, and `render.run`'s `absent` check
passed on both. The same pack with the questions var empty made no questions and no answers,
printed no answers heading, and still rendered all three documents. The model returned two
answers anyway, to questions that do not exist; with no question items they go nowhere.

### Counts

| Measure | Count |
|---|---|
| Requirements asked (all grounded in the posting) | 6 |
| Requirements kept | 1 (radio coordination) |
| Requirement gaps | 5: 3 correct (licence, sailing, certificate), 2 false (logs, berths) |
| Questions (one per line of the questions var) | 2 |
| Questions answered with a kept sentence | 1 (radio coordination, judged with its question, p=0.966), correct |
| Questions not answered | 1 (pilot licence), correct |
| Bullets kept | 7 of 11 spans, one of them a heading line |
| Letter sentences written and kept | 4 of 4 (the first holds two sentences) |
| Gaps in total (`claims.settle`) | 6 |
| Judge calls (`citations.judge`) | 8 claims |
| Invented employers, dates or certificates in rendered kept text | 0 |

Where each miss came from:

- **Mis-citation.** The logs requirement cited the berth and tide-notice spans instead of the
  lighthouse log (p=0.037 and 0.059), so it became a false gap.
- **Threshold.** "experience planning berth schedules" cited the right span. The judge gave it
  p=0.556 against a threshold of 0.6, so it became a false gap.
- **Overstatement and partial support.** "keeping accurate records of maritime information"
  rides on the tide notice (p=0.891). The first letter sentence cites the current role and the
  berth span, and also claims the coastguard work, which it does not cite. Each citation is
  judged relevant to the sentence; nothing checks that the citations cover all of it. This is
  the limit the spec names.

**The sendable documents are clean of gaps; the review sheet carries them.** Nothing rejected
reaches the letter or CV, and the unsupported question is listed for the sender, not the reader.
The letter still overstates, which only a person reading it beside `tailored.json` catches.

### Run-to-run spread at temperature 0

Two runs of the earlier two-document pack on the same store gave identical extracted PDF text
and identical counts; the PDF bytes differ. Replays of identical requests did vary, though:

- qwen: one requirement's citation was `[]` in 1 of 3 runs and `[3]` in 2 of 3.
- mistral: the (b) letter came back with 0, 6, 6 and 3 sentences over four calls.

Temperature 0 on Ollama narrows the output. It does not pin it.

## profile-ingest after the Extractor change

`profile-ingest` goes through the same Extractor, so its prompt changed too. It was measured on
the same fabricated PDF, 2 runs before the change and 2 after (identical within each pair):

| | Before | After |
|---|---|---|
| Entries | 2 | 2 |
| Claims | 11 (all 9 bullets, plus both heading lines as claims) | 6 (3 of 9 bullets dropped) |
| needs_review | 0 | 0 |
| The current role's end | "2021" (wrong) | null, ongoing true (right) |

Seeing the schema fixed the dates and the heading-as-claim noise, but lost three bullets. The
tailor pack reads spans from `source.txt`, not from claims, so tailoring does not see the loss.
A reader of `history.json` does.

## R8: tabula at a line wrap

Task 6 measured tabula on PDFs from the real `typst` binary. At a wrap inside a hyphenated word,
tabula emits `-\n` with no trailing space, exactly what `render.run`'s join targets. At a
word-boundary wrap it emits a trailing space before the newline, which `app.Ground`'s whitespace
normalising already absorbs. The templates set `hyphenate: false`, so Typst never adds a hyphen
of its own. A mutation proved the join does real work for the hyphenated case.

## Rulings made during execution

- **T3:** the relevance threshold must satisfy 0 < t <= 1. A missing judge answer is an error,
  never p=0. The question names the claim.
- **T4:** an object with a "text" key is a statement. Unless the text is a non-empty string it
  is a gap (fail closed).
- **T5:** `--root` does not stop Typst package downloads. The child process gets empty package
  directories and a dead proxy, so a fetch fails loudly. An oversize output reports the size
  limit, and the timeout error includes stderr.
- **T6:** the pack owns its template fixtures (`packs/<pack>/testdata/*.json`), so Go names no
  template wording. The PDF is written through a temp file and renamed only once verified.
  `render.run` gained `before` markers, so a gap section could not satisfy a kept
  expectation; they were removed at final review with the gap sections themselves.
- **T8:** requirements come from the posting as grounded quotes, and `items.cite` builds the
  claims. Answers are asked for only when questions are given.
- **T9:** R10 was rejected by measurement. The Extractor puts the schema in the user message.
  The earlier ruling to give `model.complete` a schema input was withdrawn, and the letter stays
  on `extract.run`.
- **Final review: gaps move from the sendable documents to a review sheet.** The approved
  design printed gaps inside the documents: the letter listed its removed sentences verbatim
  under "Removed for lack of evidence", and the CV listed requirements under "Not shown by the
  record", false gaps included. A sendable PDF therefore stated rejected claims to its reader,
  and told an employer the candidate lacks things the record shows. Now `cv.pdf` and
  `letter.pdf` carry only kept content, `review.pdf` lists every gap, and `render.run`'s
  `absent` input makes a sendable render fail if a gap text is printed. `render.run`'s `before`
  input is gone: the sendable documents have no gap section to scope away.
- **Final review, also ruled:** questions come from the questions var, never from the model
  (`text.lines`, one per line, then `items.gather`); every text object is a
  statement and no citations list is a gap; the CV prints "present" only when an entry is
  marked ongoing; kept answer sentences are verified in `letter.pdf`; dropped counts are
  recorded; `text.spans` reads one path per line.
- **Final re-review:** `absent` is searched for only outside kept content. A false requirement
  gap such as a tool name also appears inside a kept bullet quoting the record, and searching
  the whole text failed the CV render and stopped the pack before the letter and review sheet.
  An answer sentence is judged with its question in the subject, because the letter prints it
  as an answer. Questions are split from the questions var without a model call, so the
  dropped-questions count, which could no longer be non-zero, is gone.

## What surprised me

- **A constraint can be the whole failure.** A strict schema looks like pure safety, but a
  grammar the model cannot see turns "I don't know the shape" into an empty list that validates.
  Every check downstream then reported, correctly, that nothing was claimed. Nothing errored.
- **The failure was labelled twice before it was measured.** "A model-capability gap" (Task 8)
  and "the system message suppresses it" (R10) both sounded right. A proxy and five one-variable
  replays settled it in minutes.
- **The judge's errors are at the edges, not in the middle.** It rejected the mis-citation,
  but it passed an overstatement and dropped a true citation 0.044 under the threshold.
- **The model's citations are the weakest link.** A mis-cited requirement becomes a false gap,
  and a sentence citing one span can claim more than that span shows.
- **Where a gap is printed matters as much as whether it is caught.** Every check held, and the
  letter still showed the reader what had been rejected. A gap is a note to the sender.

## What I would do differently

- Put a logging proxy in front of the model on the first live run of any new pack. The captured
  request is the only honest reproduction.
- Measure each extraction step's item count on the first live run, not only the rendered PDF.
  An empty list that validates hides behind a working render.
- Keep heading lines out of the span listing, or mark them, before asking the model to choose
  bullets. A heading became a bullet here.

## What I still do not understand

- Why Ollama at temperature 0 varies between identical requests. Batching and GPU kernel order
  are the usual suspects, but not verified here.
- Why showing the schema made `profile-ingest` drop three bullets it used to keep.
- Whether the swapped span numbers come from the heading line at span 0 shifting the model's
  count, or from something else.
- The relevance judge's error rate on overstatement. The spike measured 6 of 7 on irrelevance;
  the fabricated run passed an overstatement and a partly cited sentence. A few runs are not a
  rate.

## Limits the spec states, and where they showed

- **Overstatement.** A relevant span does not stop an overstated sentence. It showed: the letter's
  "keeping accurate records of maritime information", and a first sentence that claims work it
  does not cite.
- **Headings from history.** Headings come from grounded `history.json` entries, and a grounded
  entry can carry wrong dates (Epic 6's open fix). Before this change, ingest gave the current
  role an end of "2021". After it, the end is right on this record. A heading line also entered
  the CV as a bullet through the span listing.
- **The relevance judge's measured error rate.** 6 of 7 irrelevant citations rejected in the
  spike. Here, one true citation fell under the threshold and one overstatement passed.

## Deliberately not built

As the spec's table: sending anything to an employer, a review UI, semantic search over
evidence, rewording bullets, Typst packages and fonts, fixing Epic 6's claim misattribution,
and scoring the judge against human reviews.
