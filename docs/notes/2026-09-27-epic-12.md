# Epic 12: surfaces

## What the pattern was

`TestInboundAdaptersStayIsolated` pins one property: an inbound adapter reaches the core, the
standard library, and third-party packages, and nothing else. It is enforced by walking every
package under `internal/adapters/inbound/...` and checking its dependency list, so a package
added after the test was written is checked automatically — no test needs editing when a sixth
surface arrives. `isolationViolations` is one small pure function (an allowlist: inside the module, only
`internal/core/...` and the package's own subtree); it does the classification and the
test just calls it, which is why `TestIsolationRuleSeparatesSurfaces` can pin the rule itself
against synthetic dependency lists rather than the real tree.

The four mutation proofs from Task 1 (and its two fix rounds) showed the rule holding under
every real shape a violation can take:
- **Sibling**: `packfile` importing `mcpserve` — FAIL naming both.
- **Outbound**: `packfile` importing `gitdocs` — FAIL naming both.
- **A new future package**: `zzsurface` importing `outbound/tools` — FAIL naming `zzsurface`
  and `tools`, plus a second line for `tools`'s own transitive import of `outbound/crawlsource`
  — the test caught a real dependency the brief hadn't named.
- **Vacuity**: pointing the enumeration at a nonexistent path — FAIL at "the enumeration is
  broken, not the seam", so a rule that silently checked zero packages could never pass by
  accident.
- Two round-1 fix items closed real holes: `internal/config`/`internal/telemetry` were not yet
  forbidden (mutation: `packfile` importing `internal/config` — FAIL), and a package outside
  every known home could hide from the isolation test entirely (mutation:
  `internal/zzweb` — FAIL, "has no known home").
- Round 2 fixed a cache blind spot: `go test`'s result cache does not see a package
  added or removed via `exec.Command("go", "list", ...)`, so a stale cached PASS could survive
  a real regression. `witnessModuleTree` walks the module so Go's testlog records the walk
  and the cache is correctly invalidated — proved by seeding a cached PASS, adding a violating
  package, and rerunning the same scoped command with no `-count=1`: it FAILed, not cached.

This task's own sketch (`internal/adapters/inbound/zzsketch`, deleted before commit) proved the
same property forward rather than by mutation: build the shape the web UI epic's handler will
take, run the isolation test with it present, diff `internal/core` against HEAD, then push it
one step further than "adding" — reaching into an outbound adapter — and watch the same test
catch it:

```
$ go build ./internal/adapters/inbound/zzsketch/
BUILD OK
$ go test ./internal/arch/ -run TestInboundAdaptersStayIsolated -v -count=1
--- PASS: TestInboundAdaptersStayIsolated (0.18s)
$ git status --short
?? internal/adapters/inbound/zzsketch/
$ git diff --stat HEAD -- internal/core
(empty)
```

Then, with `_ "github.com/tunedev/atlas/internal/adapters/outbound/gitdocs"` added to the
sketch's imports:

```
$ go test ./internal/arch/ -run TestInboundAdaptersStayIsolated -v -count=1
    surfaces_test.go:38: github.com/tunedev/atlas/internal/adapters/inbound/zzsketch depends on
    github.com/tunedev/atlas/internal/adapters/outbound/gitdocs; an inbound adapter may reach
    the core, never another surface, an outbound adapter, or composition-root infrastructure
    (config, telemetry)
--- FAIL: TestInboundAdaptersStayIsolated (0.21s)
```

The empty core diff is the epic's thesis stated as evidence, not assertion: a full second
surface — decode, run, encode — cost zero lines under `internal/core`.

Live evidence (Step 3) exercised progress and the pidlock end to end with a real two-step
offline pack (`file.read` twice, no model, no network): a fresh store directory that did not
exist before the first run came up clean (`err.txt` held exactly four lines — started/done for
each step, exit 0); a live holder's lock refused the second run by naming its pid in the
error and exit 1; and once that holder was killed, the same still-present lock file (still
holding the now-dead pid) was silently reclaimed on the next run, which completed with exit 0
and left `.atlas.lock` absent afterward.

## What surprised me

The sketch's only real finding was a concurrency bug hiding in a convenience: when
`WithProgress` set its field in place, sharing one `*app.Runner` across requests and calling it
per request wrote that field from every request's goroutine — a data race, invisible in a
single-pack CLI where there is only ever one caller. The isolation test cannot see this, because a data
race is not an import-graph property; nothing under `internal/core` failed, or could fail,
to catch it. The fix is at the source: `WithTracer` and `WithProgress` return a copy, so a
shared Runner is safe and each request derives its own.

The mutation proofs from Task 1 also surfaced two things no one had asked for: mutation 3's
extra FAIL line (`outbound/tools` transitively depends on `outbound/crawlsource`, so a sketch
importing one gets flagged for both) proved the checker walks the real graph rather than a
first-level import list; and the `go test` cache's blindness to `exec.Command`-driven checks
(round 2) was a real gap a careless rerun would have hidden — a mutation could sit unflagged
behind a stale cached PASS with no signal beyond the word `(cached)`.

## What I would do differently

Write `witnessModuleTree` (or an equivalent cache-invalidation guard) as part of the first
version of any test that shells out to `go list` rather than as a fix round bolted on after the
gap was found by inspection. The pattern — a test whose real check bypasses Go's import graph,
so the test cache cannot see what it depends on — is general, not specific to this seam, and
the fix is cheap enough to have been the default from the start.

## Final review wave

Each hole was proved open before it was closed.

- **Creation race.** `create` used `O_EXCL` and then wrote the pid, so a racer could read the
  empty file as garbled and steal it. Four racers (goroutines standing in for processes, each
  under a live helper's pid) on one path: 126/200 trials had more than one holder. Writing the
  pid to a temp file and hard-linking it into place: 0/2000.
- **Own pid.** A lock holding the process's own pid was refused, so a container restarted as
  pid 1 would be locked out by its own old lock forever. It is now reclaimed, and the live-holder
  test uses a genuinely separate blocking child process instead of the test's own pid.
- **Known homes.** `web/web.go`, `internal/pidlock/web/web.go` and `cmd/atlasweb/main.go` each
  passed the old internal-only, prefix-matched check. Each now fails, the first straight after
  a cached PASS with no `-count=1`.
- **Isolation.** The rule was a denylist, so `internal/pidlock` or any new module package was
  open to surfaces by default. As an allowlist, `packfile` importing `internal/pidlock` fails.
- **One registry.** A helper calling `buildRegistry` outside `run()`, in `main.go` or a second
  file, passed. Counting across all non-test files of package `main` fails both.
- **Shared Runner.** Sixteen goroutines deriving from one Runner: 13 race reports and callers
  seeing each other's events, or none. With copies: clean under `-race`, 20 repeats.

## What I still do not understand

Reclaiming a stale lock is still racy. Two processes that both read the same dead pid each
remove the lock and link their own, and the second removal deletes the first one's fresh lock.
A probe racing four live-pid acquirers against a dead pid's lock gave more than one holder in
27-41% of 500 trials. Closing it needs a take-over that re-checks what it removed, or an OS
advisory lock; it takes two atlas starts on one root in the same instant after a crash.

Hard links are assumed. They work on ext4, APFS and NTFS; a store root on a filesystem without
them (some FUSE or network mounts) fails `Acquire` loudly rather than falling back, and no such
mount was tried.
