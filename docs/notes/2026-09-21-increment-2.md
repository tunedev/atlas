# Increment 2: the provider port, and what reading a probability taught

## What the pattern was

`ports.Provider` is one interface (`Name`, `Complete`) that any
OpenAI-compatible chat-completions endpoint can satisfy. `openaiprov.Client`
is the single adapter; switching engines is a base URL and a model name, not
a Go change. The controller ran the same binary, the same two packs, against
two engines with nothing changed but `-model-base-url`/`-model-name`, and
both produced a valid, non-empty result:

- `job-hunt.yaml`: vLLM (`Qwen/Qwen2.5-Coder-7B-Instruct-AWQ`, port 8000)
  returned exit 0 with verdict `"stretch"`; Ollama (`qwen2.5-coder:7b`, port
  11434) returned exit 0 with verdict `"apply"`, both with explicit
  `-model-base-url`/`-model-name` flags and again on default config.
- `hn-summary.yaml`: exit 0 on both engines, and on default config.

Story 2.2's actual done-when is "local vLLM and a hosted key with only config
changed." That did not hold as written: only vLLM and Ollama were exercised.
No hosted key was tried in this increment. `TestAgainstALiveEngine` and
`TestMassPerClassAgainstALiveEngine` also passed against both engines
(evidence in
`.superpowers/sdd/2026-09-21-increment-2-provider/evidence-*.txt`), which
does support the underlying claim -- switching engines is config, not code
-- but a hosted key is still unproven.

The chain (`app.Chain`, Task 4) tries an ordered list of providers, each
behind its own `app.Breaker`, and returns the first completion that
succeeds. `app.MassPerClass` (Task 5) turns a completion's per-token
log-probabilities into a normalised probability per class, reading the last
token whose own text is a class member rather than the completion's final
token, so a schema-forced closing token does not get read as the answer.
Neither is wired into `cmd/atlas`: `buildRegistry` still constructs exactly
one `openaiprov.Client` from config and hands it straight to
`tools.NewModel`. The chain has no production caller this increment, by the
same ruling that scoped Task 4 — multi-provider config is its own increment.
Full description in `docs/design/the-provider.md`.

## What surprised me

**The live test's own log line was wrong, and neither of us caught it until
now.** `mass_live_test.go`'s `chosenTokenReport` logged the completion's
*last* token, not the token `MassPerClass` actually selected. Captured
before my fix: vLLM logged `text="<|im_end|>" probability=1.0000`, Ollama
logged `text="\"}" probability=0.9888` — an end-of-turn marker and a closing
brace, neither one an answer. `MassPerClass` itself was reading the right
token all along (its own tests already proved the selection rule by
mutation in Task 5); only the test's diagnostic line was pointed at the
wrong position. I rewrote it to find the same token `MassPerClass` finds —
the last token whose own text is a class member — and report that token's
own probability. Rerun against Ollama (vLLM is stopped, so this comparison
has no vLLM figure — recorded here, not invented):

```
mass per class: map[no:0.03782880663693168 yes:0.9621711933630683]
chosen answer token: text="yes" probability=0.9563
```

`MassPerClass` put 96.22% of the mass on "yes"; the answer-bearing token's
own log-probability, exponentiated, was 95.63%. Close, but not identical —
which is the point of Task 5's `TestMassIsNotTheChosenTokensProbability`:
`MassPerClass` sums every alternative that matches a class's surface forms,
not just the one token the model happened to emit, so it is reading a
slightly wider slice of the distribution than the chosen token's own
probability alone. The "last token whose own text is a class member" rule
held on both engines in the earlier evidence run (both passed with
`yes > 0.8`) and held again here; nothing in this increment's live testing
broke it. That a defect could sit in a test's *own* diagnostic output for
an entire task without failing the test is worth sitting with — the
assertion (`mass["yes"] <= 0.8` fails) was checking the number that
mattered; the `t.Logf` line was decoration nobody was reading critically
until this task asked "does this line actually say what it claims."

Plainly: on this live obvious-yes question, the emitted answer token already
held nearly all the mass (0.9563) against `MassPerClass`'s 0.9621 — close
enough that this run never exercised the case `MassPerClass` exists for,
where the model's confidence is split across more than one surface form of
the same class. Only the recorded fixture (`recorded` in
`client_test.go`, and Task 5's own unit tests) proves that rule; this live
run confirms the happy path, not the split-mass case.

**Bringing vLLM up on an 8 GB card took four failed attempts before one
worked**, all recorded by the controller in
`evidence-summary.md`: `--gpu-memory-utilization 0.90` left a negative KV
cache budget; vLLM's own free-memory check then refused 0.90 outright
because the desktop was already holding roughly 0.9 GiB of the card;
FlashInfer's JIT compile failed because the system `nvcc` is CUDA 12.0 and
does not recognize `--compress-mode=size`; and a 2048-token prefill chunk
OOMed against a 3649-token prompt. The command that finally worked:

```
VLLM_USE_FLASHINFER_SAMPLER=0 ~/.venvs/vllm/bin/vllm serve \
  Qwen/Qwen2.5-Coder-7B-Instruct-AWQ --max-model-len 8192 \
  --gpu-memory-utilization 0.84 --enforce-eager \
  --max-num-seqs 8 --max-num-batched-tokens 512
```

Each flag answers one of the four failures: `--gpu-memory-utilization 0.84`
(down from 0.90) leaves headroom for the ~0.9 GiB the desktop already holds
and for a positive KV cache budget; `VLLM_USE_FLASHINFER_SAMPLER=0` avoids
the FlashInfer JIT path that the CUDA 12.0 `nvcc` mismatch breaks;
`--max-num-seqs 8` bounds how much KV cache the server reserves up front;
`--max-num-batched-tokens 512` shrinks the prefill chunk well below the size
that OOMed on the 3649-token prompt; `--enforce-eager` disables CUDA graph
capture, which this ruling's original `global-constraints.md` command
(`--gpu-memory-utilization 0.85`, no other flags) did not need to touch
because it never got past the first two failures to reach it. This confirms
the brief's own framing of the risk (8 GB "bounds this to roughly a 7B at
four bits... `--max-model-len` is the lever") was correct in kind but
understated in degree — the lever that actually mattered most was the
prefill batch size, not the context length.

**Same job ad, same prompt, different verdict.** vLLM (AWQ quantization)
said "stretch"; Ollama (GGUF quantization) said "apply". `evidence-summary.md`
also notes vLLM applies the model's `generation_config` (temperature 0.7,
top_p 0.8, top_k 20, repetition_penalty 1.1) by default, which Ollama's
request path may not reproduce identically. Nothing in this increment pins
down whether the verdict split is quantization, sampling parameters, or
both — it is simply not the same answer, from what the harness treats as
"the same model" by name alone.

**The documents step invents experience.** Both engines' CVs and cover
letters name specific employers, dates, and (in the default-Ollama run) a
fabricated master's degree, despite the prompt saying "use only facts given
about the candidate." Nothing checks generated documents against the facts
they were supposedly built from.

**A dead engine reports nothing useful.** When vLLM's process died mid-run,
`openaiprov.Client.Complete` surfaced only `"<name> returned status 500"` —
the response body is read and then discarded on a non-2xx status, so
whatever vLLM actually said about why it failed never reaches the caller.

## What I would do differently

I would treat a test's `t.Logf` output as an assertion-adjacent claim from
the start, not a free-form comment. This line existed since Task 5, was
never wrong in a way that failed the test, and was still wrong — it claimed
to report "the chosen answer token" and reported something else. If a log
line makes a factual claim about what a test observed, it deserves the same
"does this exercise what it says it exercises" scrutiny as the assertion
next to it, especially in a note whose entire job is to compare that number
against another one.

I would also not have accepted "cost if wrong: re-run with other flags" as
license to stop at the first flag set that merely started the server. The
working command above is one specific point in a four-dimensional space
(memory utilization, batch size, sequence count, eager mode) that happened
to clear this card's constraints; nothing here establishes it is the
*right* point, only a working one. A second pass tuning `--max-num-seqs` and
`--max-num-batched-tokens` upward from their current conservative values,
now that a working baseline exists, would tell us whether this is close to
the card's real ceiling or leaving throughput on the table.

## What I still do not understand

Whether `Prompt`/`Completion` are the right shapes for a `Judge`. Both are
currently sized for "one prompt in, one completion out, optionally with
per-token data." A `Judge` (Epic 3, explicitly out of scope here) will
likely want to ask the same question of more than one candidate answer, or
compare mass across more than two classes with structure between them (a
Likert scale, not just yes/no) — nothing here proves `Prompt`/`Completion`
compose cleanly into that, only that they serve `model.complete` and a
direct `MassPerClass` call today.

Whether the "answer-bearing token is the last token whose own text is a
class member" rule survives a real multi-token or free-text answer shape.
Every case tested so far — this task's rerun, Task 5's live test, and Task
5's unit tests — uses a single-word class ("yes"/"no") behind a schema
that puts the enum value in one token. Nothing has yet asked a question
whose honest answer is not a single token (a class name with a space in it,
a class whose surface form spans a tokenizer boundary differently across
engines), so the rule's real edge is still theoretical.

I do not know whether the verdict split between vLLM and Ollama on the same
job ad traces to quantization, `generation_config` defaults, or the request
path not carrying temperature/top_p at all — `model.complete` never sets
sampling parameters on the `Prompt` it builds, so whatever vLLM applied by
default was vLLM's own choice, invisible to and uncontrolled by this code.
That the harness produced two different hiring verdicts from what it
considers "the same model" and did not surface that anywhere is worth
treating as a real gap, not a curiosity — and everything running clean
under both engines this task should be read as evidence the happy path is
well covered, not as evidence the harness handles disagreement, hallucination,
or a broken engine gracefully. It does not yet do any of those three.
