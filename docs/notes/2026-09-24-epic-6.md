# Epic 6: profile, and what "grounded" does and does not mean

## What the pattern was

Three ideas carry the whole epic, and none of them know what a CV is.

**Schema as data.** `extract.run` takes a JSON Schema as an opaque byte string and hands it
to the `Extractor` port unchanged; `app.NewExtractor` sends it as `Prompt.Schema` with a
fixed temperature and errors on anything that is not valid JSON. Turning that schema into
`response_format: json_schema, strict: true` on the wire is the `openaiprov` adapter's job
for any `Prompt` that carries a `Schema` — `app.NewExtractor` itself pins nothing about
strict mode. Nothing in `internal/core` or `internal/adapters` declares what fields a CV
has — that lives entirely in `packs/profile-ingest.yaml`'s schema block. The live proof in
Task 9 used a ship's-log schema, not a CV schema, on purpose: the tool is the same either
way.

**Grounding as a pure function.** `app.Ground(extracted json.RawMessage, source string)
([]string, error)` walks a decoded tree looking only for the structural convention `quote`,
and reports a JSON Pointer to every one that is not a verbatim, case/whitespace-normalised
substring of `source`. It takes no port, does no I/O, and knows nothing about what a quote
belongs to — its own doc comment says so. `app.Annotate` wraps it to set `status` beside
each quote and count `needs_review`. Every test in `ground_test.go` runs offline.

**Status is machine-derived, never hand-set.** Annotation is its own tool, `quote.ground`,
not a step folded into `extract.run` (R6). A correction re-grounds a hand-edited
`history.json` against `profile/source.txt` through the exact same function ingest used. A
user clears a `needs_review` flag by fixing the quote, not by typing `grounded`:
`Annotate` recomputes `status` from the quote for every quote-bearing object, and an
object that carries a `status` with no `quote` beside it is forced to `needs_review` too,
rather than left holding whatever was typed there.

One more small pattern worth naming: `RecordDocument` (Task 4, R10) is the third
put-then-index case after judgements and decisions, so it earned extraction. `docs.put`,
`decision.record`, and the profile packs all commit through it. A fourth kind of record
needs no new code, only a `Document{Kind: "whatever"}` value.

## What surprised me

**Grounded is not correct, and the gap is not rare — it happened on the first live CV
tried, and it included a dropped entry that no grounding check can catch: the model never
emitted a Northwind Logistics entry at all.** Task 11 ran `packs/profile-ingest.yaml`
against a real two-employer CV (Northwind
Logistics as Senior Engineer, 2021-03–present; Contoso Ltd as Software Developer,
2017–2021) through `qwen2.5-coder:7b`. Every one of the 8 quote-bearing objects came back
`grounded` — `needs_review: 0`:

```json
{
  "entries": [
    {
      "claims": [
        { "quote": "Senior Engineer", "status": "grounded", ... },
        { "quote": "Northwind Logistics", "status": "grounded", ... },
        { "quote": "2021-03 to present", "status": "grounded", ... },
        { "quote": "Led migration of the order pipeline to Go, cutting p99 latency by 40%", "status": "grounded", ... },
        { "quote": "Mentored four engineers", "status": "grounded", ... }
      ],
      "employer": "Contoso Ltd", "end": "2021", "start": "2017",
      "quote": "Software Developer", "status": "grounded", "title": "Software Developer"
    },
    {
      "claims": [
        { "quote": "Built internal billing tooling in Python", "status": "grounded", ... }
      ],
      "employer": "Contoso Ltd", "end": "2021", "start": "2017",
      "quote": "Software Developer", "status": "grounded", "title": "Software Developer"
    }
  ]
}
```

But the model produced two entries both labelled `Contoso Ltd / Software Developer /
2017-2021`, and never emitted a Northwind Logistics entry at all. The first entry's five
claims — including one whose quote is the literal string `"Northwind Logistics"`, the
correct employer name for everything else in that entry — describe the Northwind
Logistics/Senior Engineer role verbatim, word for word out of the source text. Only the
second entry, with its one claim about Python billing tooling, is actually Contoso's. So:
8/8 quotes grounded, 6/8 grounded **and attached to the wrong employer/title/date fields**,
and the annotator reported the document as fully clean. `quote.ground` did exactly what it
is built to do — every one of those quotes really is in `profile/source.txt` — and that is
precisely the problem: verbatim membership says nothing about which parent object a quote
was hung on.

Plainly: **ingest output cannot be trusted without reading every entry by hand**, even when
`needs_review` reads 0, until one of the following lands (neither is chosen here, both are
named in R5 and the plan's Review Focus and the ledger):

- require an object's short scalar siblings (`employer`, `title`, `start`, `end`) to also
  occur in that object's own `quote`, so a claim's proximity to its parent's label is
  checked, not just its presence in the whole document; or
- run the semantic judge-check R5 deferred — one `judge.ask` call per ingest asking whether
  each quote actually supports its parent's fields, at the cost of a model call per claim.

This was not a one-off: it was measured once while planning (R5, "the model's quote for one
entry was a verbatim bullet from that entry rather than the line naming it") and reproduced
on the very first live end-to-end ingest run (Task 11), on a CV with only two employers.

**A test that literally cannot fail passed review anyway, and only mutation caught it**
(Task 2). The brief's test for `app.Render`'s new `json` function asserted the rendered
JSON was "not HTML-escaped" by checking `!strings.Contains(got, "&amp;")` and similar
entity strings. That assertion can never fail either way: Go's `json.Encoder` with
`SetEscapeHTML(true)` emits the six-character escape sequence \u0026 (and \u003c for
`<`), not `&amp;` — HTML escaping was never the encoding Go's own encoder does, so a
test written against HTML entities is checking for a failure mode the code cannot
produce. It passed on the first implementation for the wrong reason.
Review caught it by mutation: flipping `SetEscapeHTML(false)` to `SetEscapeHTML(true)` and
re-running left the test green, which is the signal that it was not discriminating. The
fix changed the assertion to check for literal `&`/`<` characters directly (which
`SetEscapeHTML(false)` is what actually produces), and the same mutation then failed the
test as expected. "Proved by mutation" is only as good as the property the assertion
actually names.

**A judgement-shaped decision test proved something real.** Task 12's live run of
`packs/decide.yaml`, pointed at a judgement `decide.yaml` did not itself compute, came back
`verdict_at_decision: "no"` — matching the `stretch.chosen` value `packs/job-hunt.yaml` had
printed earlier from the same judgement document. `app.VerdictAt` re-reads the verdict from
the stored judgement rather than trusting a caller-supplied value, so a decision document
snapshots what the judgement actually said, not what the pack's vars claimed it said.

**The live extraction schema test found nothing to complain about, which is itself
informative.** Task 9's `TestExtractAgainstALiveEngine` used a nested schema
(`voyages[].events[]`, a `start` field with a date-`pattern`) against the same engine and
model as the CV run, and came back `ungrounded quotes: []` — every quote verbatim, both
`start` values matching the pattern. The schema-adherence and verbatim-quoting halves of
extraction are solid on this model; it is cross-referencing a quote to the correct sibling
object where it fails. That is a narrower, more specific failure than "the model
hallucinates," and it is exactly the shape R5's judge-check or a proximity check would
target.

**`tabula` recovers from real corruption silently.** Measured while planning and confirmed
in Task 10: a PDF with its xref table removed, or `startxref` pointing at garbage, comes
back with recovered text and no `Warning` at all — not a degraded warning, nothing. A PDF
with shifted object offsets errors instead. The spec's planned test ("a corrupt fixture
reports a warning") was consequently unwritable as specified (R9); Task 10 asserts the
recovered text and passes `warnings` through with no test that asserts on a warning that
cannot exist.

## What I would do differently

I would have run Task 11's live two-employer ingest before finishing Task 6's `Ground`
tests, not after. The misattribution shape was already known from planning (R5) before any
code was written, and the fixtures in `ground_test.go` are all single-entry or
clearly-disjoint multi-entry cases (`sightingsSource`) — none of them exercise "two sibling
objects whose quotes are each individually verbatim but swapped between parents." That is
exactly the gap increment 3's note already named for a different reason ("a fixture built
entirely from single-token answers cannot discover a bug that only exists between
tokens"): a fixture that is individually correct in every part can still fail to represent
the failure mode that matters, and only a real multi-entry input surfaced it here too.

I would also fold the entry/claim proximity check into this epic rather than deferring it,
if I were re-planning from scratch — not because it is cheap, but because R5's own
reasoning ("Task 12's note measures how often it happens on a real CV before anyone pays
per-claim model calls for it") has now been answered: it happens on the very first attempt,
on a two-employer CV, at a 6/8 rate. That is evidence enough to act on rather than defer
again.

## What I still do not understand

Whether the proximity-check fix (siblings must occur in their own quote) would have caught
this specific case, or whether it needs to be stricter. Entry 1's own `quote` field is
`"Software Developer"` — a real, verbatim substring of the CV, and the correct title for
*Contoso*, not for the Northwind-shaped claims sitting under it. A same-object proximity
check comparing `employer`/`title` against that entry's own `quote` would still pass,
because `"Software Developer"` genuinely is that entry's quote; the mismatch is between the
entry's fields and its *claims*' content, not between the entry's fields and its own quote
string. I don't know yet whether the right fix checks quote-to-sibling-field membership
scoped to the whole entry subtree (entry fields against every claim's quote, not just the
entry's own), or whether that is still gameable the same way, or whether nothing short of
the judge-check actually closes this.

I also don't know how this generalises past two employers. Every measurement here (planning
and Task 11) is a two-entry CV. Whether a three- or four-employer CV produces more
mislabelled entries, the same rate, or something structurally different (the model running
out of distinct entries to invent and merging three into two, say) is unmeasured.

## What was deliberately not built

From the spec's own list, unchanged by this plan:

| Out | Why |
|---|---|
| The `cana` `/extract` adapter | Second `Extractor` implementation; the endpoint does not exist yet |
| OCR for scanned CVs | Needs system binaries via tabula's `-tags ocr` build; out until a real scanned CV is in front of us |
| Shelling out to `pdftotext` | Only worth it once tabula's pure-Go extraction is measured insufficient on a real CV |
| Automatic classification of a deal-breaker as `comparable` or `judged` | Misclassifying one silently disables it; the user states it explicitly |
| Evaluating deal-breakers against postings | Epic 7's job; this epic only defines the shape |
| A UI for corrections | Epic 12; corrections are file-edit-plus-pack for now |
| Full-text or semantic search over the evidence corpus | Epic 9's job |
| Per-claim semantic judging by default | Available via `judge.ask`; not mandated, to keep ingest to one model call by default |
| DuckDB indexing of profile revisions | No query scans profile history yet |
| The rendering toolchain (Typst, Tectonic, or otherwise) | Epic 9 story 9.5 decides, with real tailored output in front of it |

Ruled out by this plan, not the spec:

- **Purge (R3).** Deletion means removing a document from history, not only from HEAD.
  That breaks `Docs`'s no-overwrite invariant and needs its own design; added to the
  roadmap as story 6.6 rather than built here.
- **Schema validation of hand-authored JSON (R8).** `docs.put`'s `expect: json` checks
  well-formedness only, not shape. Real schema validation needs a JSON Schema library and
  has no consumer until Epic 7 parses these documents anyway.

Recorded as a broken window, not fixed in this increment: `README.md`'s and `CLAUDE.md`'s
`## Status` sections still read "Design, no code" / "`internal/` does not exist", which is
no longer true — twelve tasks of code landed on `epic-6` this increment. Left for whoever
next touches either file, rather than expanded here past this note's scope.

Deferred minors, from the controller ledger (`progress.md`), none of them blocking:

- Task 4: a failed put now reports `"judgement: record: put <path>: ..."` instead of the
  pre-refactor `"judgement: put: ..."` — names the path, which the old text did not; neither
  form is under test.
- Task 5: `file.read`'s over-limit error reads "response exceeds max size" — wording shared
  with `readLimited`'s other caller, not specific to a file.
- Task 10: `file.text` reads its input file twice — once through `readFile` to check the
  size bound and compute the SHA-256, once through `tabula.Open` by path — because the
  bound check has to gate the tabula call, not follow it.
- Task 12: the no-second-decision-overwrites-the-first test runs against fakes only; the
  spec's Testing table asked for the real `gitdocs`/`sqlindex` adapters, as
  `judgementrecord_test.go` does for the equivalent judgement case.
- `docs.put` gives no signal that a byte-identical put changed nothing: a caller cannot
  tell a no-op commit from a real one.
- An extraction reply cut off at `-extract-max-tokens` surfaces only as `"extract: reply
  is not json"`; the truncated reply is not distinguished from any other malformed one.
