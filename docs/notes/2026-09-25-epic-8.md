# Epic 8: local crawling, and the gap between a plan's sample code and a library's real behaviour

## What the pattern was

One conduct gate, assertions as tests, and targets as data.

**One conduct gate.** `crawlsource.Conduct` is an `http.RoundTripper` and the crawler's only
way onto the network. It owns robots.txt, the per-host minimum gap, the identified user
agent, method and credential refusal, the body bound, revalidation and retry — all in one
place. Colly's own robots handling and body limit are switched off (`IgnoreRobotsTxt =
true`, `MaxBodySize = 0`, each with a comment saying where the rule is actually enforced),
and the renderer calls the same `Conduct.Allow` before every navigation. A rule enforced in
two places drifts; this keeps it enforced in one.

**Assertions as tests.** Stories 8.2 (politeness) and 8.6 (never authenticated) are not
features with their own code path — they are properties of `Conduct`, proven end to end in
`conduct_test.go` against recording `httptest` servers, each guard confirmed by mutating the
production code and watching the specific test fail. `internal/arch/conduct_test.go` adds
static guards on top: no credential-shaped field in `Config`, no `cookiejar` import, no
`launcher.New()` without `.Bin(` chained onto it.

**Targets as data.** What to crawl and how to read each page arrives as pack YAML, decoded
strictly by `crawlsource.ParseTargets` the same way `judge.ask` takes `questions`. A target
has no field for headers, cookies or credentials, so a pack cannot express authentication.
`internal/arch/vocabulary_test.go` keeps every job-hunt word — `title`, `company` — out of
the Go tree; the fixtures crawl a library's talks and workshops instead.

## What surprised me

**The plan's own robots.txt sample code silently allowed everything on a failing
robots.txt, and a test caught it before any commit landed.** D9 requires "a 5xx or an
unreachable robots.txt disallows everything." The brief's sample `Allow` got a
`*robotstxt.Group` via `RobotsData.FindGroup(agent)` and called `Group.Test(path)`. Running
`TestConductDisallowsEverythingWhenRobotsFails` as written:

```
$ go test ./internal/adapters/outbound/crawlsource/ -race -v
=== RUN   TestConductDisallowsEverythingWhenRobotsFails
    conduct_internal_test.go:122: err = <nil>; a 5xx robots.txt must disallow the host
--- FAIL: TestConductDisallowsEverythingWhenRobotsFails (0.02s)
```

Reading `github.com/temoto/robotstxt@v1.1.2` and confirming with `go doc`: `disallowAll()`
calls `robotstxt.FromStatusAndBytes(503, nil)`, which returns the library's package-level
`disallowAll` sentinel — a `RobotsData` with `disallowAll: true` but a **nil `groups`
map**. `RobotsData.FindGroup(agent)` never looks at that flag; it only walks `r.groups`,
and with nothing to find falls back to the library's own empty group, whose `Test` returns
`true` ("no restrictions") by default. The disallow-all sentinel was silently being read as
allow-all. Only `RobotsData.TestAgent(path, agent)` actually consults `allowAll`/
`disallowAll` before falling back to `FindGroup`+`Group.Test`. The fix switched the disallow
check to `data.TestAgent(...)`, kept `FindGroup` only for reading `Group.CrawlDelay`, and
changed no test assertion. Confirmed the corrected code discriminates by deleting the
`TestAgent` check and re-running the same test:

```
$ go test ./internal/adapters/outbound/crawlsource/ -run TestConductRefusesAPathRobotsDisallows -v
    conduct_internal_test.go:89: err = <nil>, want ErrDisallowed
--- FAIL: TestConductRefusesAPathRobotsDisallows (0.02s)
```

Had this shipped as written, "unreachable robots.txt disallows everything" — a politeness
floor the plan states as a hard requirement, not a nice-to-have — would have been backwards
in production while every other test in the suite stayed green, because nothing else in the
brief's sample code exercised the sentinel's zero-value shape.

**A cookie assertion, as first written, could not fail — a test that cannot fail is not an
assertion.** `TestConductNeverSendsACookieBackOrACredential` ran two targets against one
host and checked no request carried a `Cookie` header. Deleting `c.DisableCookies()` from
`source.go` — the exact guard the test exists to prove — left the test green:

```
$ go test ./internal/adapters/outbound/crawlsource/ -run TestConductNeverSendsACookieBackOrACredential -v
--- PASS: TestConductNeverSendsACookieBackOrACredential (0.04s)
```

Root cause, read out of `source.go`: `s.fetched` builds a brand-new `colly.NewCollector`
— and therefore a brand-new, empty cookie jar — for every target, and calls `c.Visit`
exactly once against it. Two targets against one host means two disposable jars; nothing a
server sets on request 1 can ever be replayed on request 2, whether or not
`DisableCookies()` is called and whether or not `refuse` checks for `Cookie` by name. The
mutation the brief specified was real, but the fixture around it structurally could not
observe the guard it was meant to prove. The controller's ruling was to strengthen the test
rather than accept the false green: add a same-host case where `/start` sets a cookie and
302-redirects to `/events` within one `Visit`, and assert both that `/events` carried no
`Cookie`/`Authorization` header and that the crawl still returned items — so a jar that
makes `refuse` reject the redirect also fails the test, not just a jar that silently drops a
header. Both mutation variants (deleting `DisableCookies`; deleting it and renaming
`refuse`'s `"Cookie"` check) bite after the fix:

```
$ go test ./internal/adapters/outbound/crawlsource/ -race -v -run TestConductNeverSendsACookieBackOrACredential
    conduct_test.go:221: err = crawlsource: a (fetch): ...: crawlsource: http://.../events carries Cookie: the crawler never sends a credential
--- FAIL: TestConductNeverSendsACookieBackOrACredential (0.06s)
```

**Politeness state rebuilt per `crawl.pull` call meant two steps in one pack could double
the rate to a host.** `crawl.pull` originally called `crawlsource.New` once per invocation,
which built a fresh `Conduct` — a fresh robots.txt cache and a fresh per-host turn map —
every time. Two `crawl.pull` steps hitting the same host in one pack run were therefore
never paced against each other; politeness held only *within* a single step, not across the
pack. The fix restores the invariant at the source rather than teaching the tool to cope:
`crawlsource.Crawler` is built once in `run()` from `cfg.Crawl` and injected into
`buildRegistry`; every `crawl.pull` invocation calls `Crawler.Source(targets)`, which shares
one `Conduct` and one browser. The state belongs to the process lifetime, not to a single
tool call — the same shape the global tenets ask for ("async/expensive setup belongs at
startup, done once, injected as a value"). Proved with a test comparing the last request
timestamp of invocation 1 against the first request timestamp of invocation 2, not the last
two timestamps of the run as a whole — an earlier draft of that comparison passed even
against the buggy per-invocation code, because each invocation's own robots.txt-then-page
fetch happens to incur one internal `Delay` wait regardless of whether pacing carried over.

**Colly's body limit truncates rather than fails, and Rod's defaults fight the plan's own
requirements.** Measured while planning and confirmed in Task 2's implementation: Colly's
`MaxBodySize`, when set above zero, wraps the body in `io.LimitReader` and truncates
silently — the opposite of "an over-limit body fails rather than truncates," so `Conduct`
enforces the bound itself and Colly's own limit stays off (`MaxBodySize = 0`). Separately,
Rod's default user agent is a fake desktop Chrome string
(`Mozilla/5.0 (Macintosh; ...) Chrome/114`), which the renderer overrides with the
crawler's own identified UA via `proto.NetworkSetUserAgentOverride`; and `launcher.New()`
alone auto-downloads a browser — `.Bin(path)` must be chained directly onto it to turn that
off, confirmed by `internal/arch`'s guard that only recognises that literal chain and fails
closed on anything else, including an innocuous-looking split across two statements.

**The live run matched every acceptance point in the plan, on the first attempt.** Against
`packs/crawl-watchlist.yaml` and a local fixture site:

```
"_meta": { "count": 5, "failed": 3, "fetched_at": "2026-09-25T21:04:38Z", "revalidated": 0 }
```
with failures exactly `private`/`disallowed`, `app`/`needs_rendering`,
`moved`/`extraction_stale`, and `roles._meta.merged: 1` for the Northwind duplicate spelled
two ways across `openings.html` and `board.html`. Rerunning immediately:

```
"_meta": { "count": 5, "failed": 3, "fetched_at": "2026-09-25T21:04:54Z", "revalidated": 4 }
```

— all four pages fetched on the first run (`openings`, `board`, `app`, `moved`; `private`
was never fetched, disallowed by robots.txt before any request) were cached on their 200
and served 304 on the rerun, counted revalidated. Revalidation is about the fetch, not
about whether extraction then found an item: `app` and `moved` are still failures
(`needs_rendering`, `extraction_stale`) on this run too, revalidated or not. With
`-crawl-render` against the application-shell target, both items the page's
own script inserts after a 200ms `setTimeout` came back, and the server log shows the
crawler's own UA — not Chrome's fake default — on the `/app.html` request:

```
127.0.0.1 - - [25/Sep/2026 22:05:01] "GET /app.html HTTP/1.1" 200 - UA=atlas-crawler/0.1 (+https://github.com/tunedev/atlas)
```

confirming the user-agent override reaches the real navigation, not just the robots.txt
check. The render itself, measured in Task 7's offline test, took 1.81-1.86s end to end
(browser launch, navigate, 300ms DOM-settle wait, extract) against a local, already-running
Chrome — no download, no network round trip past the fixture server.

## What I would do differently

I would `go doc` a third-party library's actual public API before transcribing a plan's
sample code verbatim, even when the plan's authors measured against that library while
planning. The robots.txt defect above was in code the plan itself specified, written by
someone who had the library open; it still called the wrong method for the exact behaviour
D9 requires, and only a test with a directly opposing expectation caught it. The lesson
generalises past this one bug: "the plan measured this library" is evidence the library
exists and roughly does what's claimed, not evidence every line of sample code calls it
correctly.

I would also design the "Conduct's state belongs to the process lifetime" rule explicitly
into Task 1 or Task 6, not let it surface as a Task 10 finding after `crawl.pull` had
already shipped built-per-invocation. D7 states a crawl is serial and D9 states delay is
enforced in code, but neither spells out that the enforcement has to span every `crawl.pull`
call in a pack, not just one. Once stated as a Task 10 finding it was obvious and cheap to
fix at the composition root; stated up front, the per-invocation `crawlsource.New` path
would never have been built at all.

## What I still do not understand

Whether the render path's sub-resource traffic — the page's own XHR, image and stylesheet
loads, made by the browser and never checked against `Conduct.Allow` (D8) — could in
practice hit a host hard enough to violate the per-host turn that document navigation
respects. The plan states this gap plainly and the note repeats it below, but nothing
measures how much traffic a real rendered page generates outside `Conduct`'s view; the
fixture site's `/app.html` makes no sub-resource requests at all, so the live run gives no
evidence either way.

Whether the robots.txt fix (`TestAgent` for the disallow check, `FindGroup` only for
`CrawlDelay`) holds the same way across every group shape the library supports — nested
user-agent blocks, wildcards, multiple matching groups with conflicting rules. The fix was
verified against the plan's own disallow-all sentinel and the fixture site's flat
`Allow`/`Disallow` rules, not against every shape `robotstxt` parses.

Whether per-rune `ToLower` case-folding in `items.dedupe`'s key normalisation
(deferred at Task 9) under- or over-merges on a real non-ASCII site — `straße` against
`STRASSE` is the named example, and nothing in the fixtures or the live run is non-ASCII.

## What was deliberately not built

From the brief:

- fuzzy deduplication — D6 is an exact match on normalised key fields only;
- concurrent crawling — D7: a crawl is serial, turns are still kept per host, and
  concurrency buys nothing at the rates politeness allows;
- sub-resource politeness inside a rendered page (D8) — only the document navigation passes
  through `Conduct.Allow`; the page's own sub-resource and XHR loads are made by the browser
  directly;
- link-following crawls — a target is one page; nothing here discovers a page from another;
- wiring `crawlsource` as the composition root's `ports.Source` — `source.pull` stays on the
  feed; `crawl.pull` is its own tool, not a second implementation swapped in behind the same
  port;
- joining the feed and the crawl in one pack — the same `items.dedupe` step run over two
  lists, but it needs the network to prove, so it is left to the user.

**Pacing is per process.** Task 10's fix makes one process's `crawl.pull` calls share one
`Conduct` and stay paced against each other for the life of that process. It does not make
two processes paced against each other: two separate `atlas` runs started back to back, or
run concurrently, against the same host are not aware of each other and can double the
effective rate to that host. Nothing in this epic coordinates across processes.

Deferred minors, from the controller ledger (`progress.md`), none of them blocking:

- Task 1: `expandPaths`'s doc comment does not mention `Crawl.CacheDir`; the `Crawl` field
  sits after `Extract` in `Config`, not after `Feed` as the interface note said.
- Task 2: `Allow`'s doc comment carries a seven-line rationale for calling `TestAgent`
  instead of `Group.Test`; could tighten to one clause.
- Task 3: revalidation cache files are written without locking — moot under a serial crawl,
  and a corrupt entry self-heals by being refetched (`TestACorruptCacheEntryIsIgnored`).
- Task 4: a `Retry-After` in the HTTP-date form falls back to exponential backoff; only the
  delta-seconds form is honoured.
- Task 5: `javascript:`/`mailto:` href values pass through extraction unfiltered — the
  crawler never follows a link it extracts, so a downstream consumer must not fetch one
  blindly.
- Task 6: `colly` was listed `// indirect` in `go.mod` after Task 6 landed; resolved as a
  side effect of Task 7's `go mod tidy` when Rod was added, not left outstanding.
- Task 8: `TestConductWaitsItsTurnPerHost` exercises one host; per-host independence is
  proven separately by `TestConductSpacesRequestsToOneHostButNotAcrossHosts`.
- Task 9: case-folding is per-rune `ToLower`, not full Unicode folding.
- Task 10: the shared `Conduct` relies on the pack runner staying sequential; revalidation
  cache writes are still unlocked.
- Task 11: the UA-logging wrapper around `python3 -m http.server`, needed because the stock
  server's access log omits the `User-Agent` header, is not committed to the repo — the
  proof needed it once, to show the evidence above.
