# Epic 4, story 4.7: a real agent, end to end

Story 4.7 asks for a real ACP agent driving a real pack, with the evidence pasted. Until now
every test of the agent path ran against a scripted stub. This note records the first real
run. It needed no code change, only config, as `docs/specs/2026-09-24-epic-4-agent.md`
predicted.

## What ran

| Piece | Version |
|---|---|
| Adapter | `@agentclientprotocol/claude-agent-acp@0.81.2`, installed globally by the machine owner |
| Agent | Claude Code 2.1.283, model `claude-opus-5-5` (from the adapter's own log) |
| Node | v24.21.0 |
| atlas | `3b0da73`: `main` at `304cedc` plus a test-only change (PR #41) |
| Pack | `packs/agent-hn.yaml`, item 8863 |

```
atlas -pack packs/agent-hn.yaml \
  -store-root $S/store -store-index-path $S/index.db -store-history-path $S/history.db \
  -agent-command claude-agent-acp -agent-workdir $S/work -agent-tools http.request
```

`$S` was a throwaway directory. No permission rules were configured, so every decision fell to
the default, `ask`, on the terminal prompt.

The pack tests the whole path in two steps. `brief` asks the agent to fetch a Hacker News item
through atlas's own `http_request` tool, which it reaches over MCP, and then to write a file.
`check` resumes the same session (`resume: "true"`) and asks for the file's first line back.

## What surprised me

**Finding 1: the agent's built-in tools reach atlas's policy only when the agent chooses to
ask.** The spec's Permissions section says the adapter "asks `ports.Permission` before invoking
any tool regardless of whether the agent itself asked". That holds only for atlas's registry
tools, which run inside atlas behind `mcpserve`. The agent's own Read, Write and Bash run inside
the agent process. atlas advertises no file system or terminal to the agent, so it never
executes those calls and cannot refuse them. `acpagent.onRequest` answers
`session/request_permission` and nothing else, and that is atlas's only chance to decide.

Run 2 shows the gap: `Write` asked (kind `edit`), and `Read` ran without asking. Which
built-in calls ask is the adapter's own permission mode, not atlas config. What actually
bounds the agent's built-in tools today is:

- `-agent-workdir`;
- `AgentEnv`, which strips atlas's variables;
- the adapter's own mode.

The spec's claim should be read as covering registry tools only.

**Finding 2: one registry tool call is asked about twice.** The agent's ACP permission request
names the tool as the agent sees it (`mcp__atlas__http_request`, kind `other`). The MCP call
that follows is asked again by `mcpserve.handle` under the registry name (`http.request`, kind
`atlas`). Both gates are correct on their own, and the second is the one that runs the tool.
Together, though, a person answers twice for one action. Permission rules also have to name the
tool both ways, because `http.request:atlas:allow` alone still leaves the first prompt asking.

## What I would do differently

Configure rules before the first real run. `mcp__atlas__*` could allow at the ACP layer and
leave the decision to `mcpserve`, the gate that knows the registry name. Whether that belongs
in config or code is not decided here; see the open question below.

## What I still do not understand

- Whether the ACP-layer ask for an `mcp__atlas__*` tool should be answered by rule, so that
  `mcpserve` is the one gate for registry tools. The alternative is to keep both, as defence
  in depth against an agent that rewrites the call between the two. This is a design decision,
  left open.
- Which built-in tools the adapter's default mode asks about, beyond this run's evidence
  (Write asks, Read does not). This is the adapter's behaviour, not atlas's. It needs its own
  investigation before anything relies on it.
