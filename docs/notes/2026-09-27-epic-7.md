# Epic 7 note: fit judgement

## What the pattern was

One interface (`ports.Judge.Ask`), one schema per call (`app.AnswerSchema`), and one generic
tool (`judge.each`) built over ports that already existed (`Source`, `Judge`, `Docs`, `Index`)
rather than a job-hunt-specific loop. A board is scored by fingerprinting each item's rendered
subject together with its question set, its rules, and each rule's mapped field value; an item
whose fingerprint is already recorded is reused, not re-asked. Rules split into two kinds in
one call: numeric ones checked in code against a mapped field, worded ones asked as an extra
yes/no question — both report `tripped`, `clear` or `unknown`, and both flag a verdict without
ever overriding it. The same shape scores one role (`judge.ask`) or two hundred (`judge.each`);
nothing about scoring at scale needed a second interface.

## What surprised me

**Naming a question's options in its prompt exposed a real ambiguity, not a cosmetic one.**
Task 1's fix (`promptUserMessage` now lists `id: ask (one of: a, b, c)`) was meant to raise
coverage — and did, per the spec's 40-subject measurement (0.00 to 0.81 coverage on a
five-option choice question). But the live "before" and "after" runs on
`TestJudgeAgainstALiveEngine` told a second story: *before* the fix, the run passed cleanly.
*After* it, the same live call failed outright:

```
judge_live_test.go:100: live ask: judge: warmth: "co" is ambiguous between cold and cool (alternative "co", p=0.0031)
```

Naming `cold` and `cool` in the prompt made the engine more likely to emit a low-probability
truncation ("co") that is a valid prefix of both — and the existing ambiguity guard correctly
refused to guess, taking the whole call down with it. The root cause was not the prompt change;
it was that any two options sharing a first character can be made ambiguous by *some* truncation,
and naming options just made that truncation likelier to surface on live traffic. The fix
landed at the source: `AnswerSchema` now rejects an option set where two different options
share a first character, before the provider is ever called. After the fix, the same live suite
passed clean:

```
judge_live_test.go:96: live: warmth chosen="cool" mass=0.9899 ... coverage=2/4
--- PASS: TestJudgeAgainstALiveEngine (1.24s)
```

This is also why this epic's verdict is `apply`/`reach`/`skip` rather than the roadmap's
original `apply`/`stretch`/`skip`: `stretch` and `skip` share an initial.

**A wording rule needs its own question asked directly; deriving it from a statement is not
close enough.** Task 4 measured whether a judged rule's yes/no question should be worded
directly (`ask`) or derived automatically from its `statement`. The first sample (1 positive of
40 real roles) showed no difference and nearly closed the question the wrong way. A second,
class-balanced sample (20 true positives, 20 true negatives, drawn from the same board because
its 40 positives alone filled both quotas) reversed the finding completely: the derived
wording scored **0/20 on true positives** (mean p(yes) 0.20, never crossing the 0.5 threshold
used for accuracy) while the direct wording scored **15/20** on the same positives. Overall
accuracy went from derived 0.500 / direct 0.875 on the balanced sample, a result the unbalanced
first sample could not have shown. The fix: `app.ParseRules` now rejects a judged rule with no
usable `ask`, and `RuleQuestion` no longer derives wording from `Statement` at all — a rule's
question is only ever asked the way its author wrote it.

## What I would do differently

Run Task 4's rule-phrasing probe against a class-balanced sample from the start, drawn from
more than one board. The first, unbalanced sample (1 true positive of 40) was nearly enough to
ship the wrong default — a derived question that never trips on a real positive — because it
had almost no positives to be wrong about. The enriched sample fixed the accuracy question but,
by scanning boards in a fixed concatenation order, drew its entire balanced set from one board;
the second board's phrasing and formatting were never exercised. A stratified sample across
both boards from the first pass would have caught both issues in one measurement instead of
two.

## What I still do not understand

Why the live engine's shared-initial truncations appeared only after options were named in the
prompt, not before. The mechanism proposed (naming an option's text raises the probability of
short continuations of that same text as low-probability alternative tokens) fits the observed
behaviour, but it was not measured directly against the unchanged prompt on the same subjects —
the "before" run for the analogous coverage test did not reproduce a comparable baseline either
(it measured 1/5 coverage rather than the spec's headline 0.00, because the alternative
happened to already be present for that particular subject). Whether a different engine would
show the same shift, or whether it is specific to `qwen2.5-coder:7b`'s tokenizer, is untested.

Both runs against a local crawl of the GitLab Greenhouse board (199 open roles, `qwen2.5-coder:7b`,
rules loaded from `profile/dealbreakers.json`):


`salary-floor unknown: compensation.min not in the subject` (the mapped field is absent from a
Greenhouse posting, so the numeric rule is correctly `unknown`, never a false trip). No row
errored.

**Second run** — same pack, same board, nothing re-asked:


**Verdict split** (first run, 199 roles): `apply=190 reach=9`. Every `reach` verdict spot-checked
