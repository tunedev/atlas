# Increment 1: the record and its two derived indices

## What the pattern was

The increment ships two rebuild walks, not one, because its two indices are
two different shapes. `app.Rebuild(ctx, docs, idx, extract)` resets the
index, `List`s every current path from `Docs`, `Get`s each one, hands it to
a caller-supplied `extract` function, and `Upsert`s what comes back — one
row per path. That is correct for `sqlindex`, which keys on `path` alone and
only ever holds the current state.

`duckindex` keys on `(path, rev)` and holds every revision, so a single
current-state walk pointed at it would `Reset` the index and then insert
only the current revision of every path, discarding every prior revision
permanently even though git still holds them. `app.RebuildHistory(ctx,
docs, idx, extract)` is the walk for that shape: for each path, walk its
full `History` and read every revision with `GetAt`, setting each record's
`Rev` and `When` from that revision's own `DocMeta` after `extract` runs.
Extraction (interpreting a body into `Kind` and `Fields`) and the walk
(which revisions to visit, and what identity to stamp on the result) are
separate concerns; one function cannot serve both index shapes because the
walk itself is policy, not just the extractor.

`extract`'s signature (`func(path string, body []byte) (ports.Record, bool)`)
is what keeps both walks generic. `internal/core/app` does not know what a
"record" means for any use case; it only knows how to drive one function
across the paths and revisions a given walk visits. `extractItem`, written
in the test file because nothing in `internal/core` may name use-case
vocabulary, is a disposable stand-in that indexes `items/*` by a `state:`
line (and optional `rev:`/`when:` lines, read only so a test can prove those
fields round-trip too) and returns `false` for everything else — proof that
both walks correctly skip what `extract` rejects (`other/three.md` never
appears in `Find`'s results).

Two tests prove the property, one per index shape, both against real
adapters — no fake stands in for either `Docs` or `Index`. The `sqlindex`
test opens a real `gitdocs.Store` and a real `sqlindex.Index`, rebuilds
once, deletes the SQLite file from disk, reopens a fresh one, rebuilds
again, and compares the two `Find` results (sorted by path first, since
`Find` makes no ordering promise). The `duckindex` test does the same
against three revisions of one path, asserting all three come back with
distinct field values and distinct revisions after the index file is
deleted and `RebuildHistory` runs again. A third test seeds `sqlindex` with
a row whose path is absent from `Docs` and asserts it is gone after
`Rebuild` — this is the one that actually pins "reset before indexing,"
which the happy-path test cannot: an implementation that upserts without
ever resetting would still pass the happy-path test (a fresh index just
accumulates correctly) while leaving every deleted document's row behind
forever.

`Store.Root`, `Store.IndexPath` and `Store.HistoryPath` are real, validated
config — flags, environment variables, tilde expansion, empty-value
rejection — but nothing in `cmd/atlas` constructs a `gitdocs.Store` or
either index. Config that is checked at startup but not yet read by
anything is fine; the adapters that would actually open those paths have no
consumer this increment. Running either pack creates nothing under
`~/.atlas`.

## What surprised me

Mutation-testing the two tests confirmed something the brief predicted but I
would have gotten wrong by intuition: deleting the `idx.Reset(ctx)` call
entirely left `TestDeletingTheIndexAndRebuildingLosesNothing` **passing**.
That test only ever runs against an index that starts empty or was deleted
and reopened from scratch, so "reset first" is invisible to it. Only the
second test, which pre-populates a stale row that has no business surviving,
turns that mutation red. This is a recurring pattern in this increment: more
than once already, a test passed while asserting nothing the implementation
could actually get wrong, and this task would have added another instance
if the brief had not named the second test explicitly up front. I would not
have found this by inspection; I found it by actually deleting the line and
running the suite.

The second mutation (dropping the `idx.Upsert` call, leaving `_ = rec`) was
caught immediately by the happy-path test's own self-check
(`if len(before) == 0 { t.Fatal(...) }`), which exists precisely so the test
cannot pass by finding nothing on both sides of the delete-and-rebuild.

The larger surprise was structural: a single rebuild walk cannot serve both
index shapes, and the failure mode is not a crash but silent, permanent data
loss. `Rebuild`'s current-state walk (`List` then `Get`, one `Upsert` per
path) is exactly right for `sqlindex`. Pointed at `duckindex`, which is one
row per `(path, rev)`, the same walk would `Reset` the index and then
re-insert only the current revision of every path — every prior revision
gone, with no error anywhere, because nothing about that operation is
invalid; it just isn't what a revision-keyed index needs. "Delete both
indices, rebuild from git alone, lose nothing" is a claim about two indices,
and having a passing test for one of them is not evidence about the other —
they needed separate tests because they needed separate code.

Also worth recording plainly: `time.Time{}` round-tripped through
`sqlindex`'s storage (`When.UTC().UnixNano()`, then `time.Unix(0,
whenNano).UTC()`) does not come back as `IsZero()`. A zero `time.Time` is
year 1, whose Unix nanosecond value overflows `int64` and wraps to some
large, non-zero, non-meaningful number instead of `0`. This was not this
increment's bug to fix, but a test written to check "no meaningful `When`
was set" by asserting `IsZero()` would not catch a genuinely unset one that
went through this storage path — it would need to check for the wrapped
sentinel value instead, or the schema would need to store an explicit
absence rather than relying on the zero value's numeric form.

I did not hit any go-git behavior that surprised me in this task. `Rebuild`
calls `docs.List` and `docs.Get`; `RebuildHistory` calls `docs.List`,
`docs.History`, and `docs.GetAt`. All four were already exercised end to
end in Tasks 1-4's own test suite; nothing here exercised a new corner of
go-git.

## What I would do differently

I would write the reset-first test before the happy-path test, not after.
Writing it second meant I only confirmed by mutation, after the fact, that
the happy-path test could not have caught that bug on its own — writing it
first would have made that gap visible from the test list alone, before any
code existed to hide it.

I would also test a shared function against every shape it is meant to
serve before calling the property proven, rather than against one shape and
assuming the others are symmetric. `Rebuild` and `sqlindex` looked like a
complete demonstration of "rebuild from git alone loses nothing" on their
own; `duckindex` existing as a second, differently-shaped `Index`
implementation in the same package was the fact that made that assumption
wrong, and it was available to check from the start.

I would also be more suspicious of an instruction to open a resource nothing
consumes yet. "Open it so a bad path fails loudly at startup" sounds like a
reasonable justification for constructing an adapter with no caller, and it
is not: a composition root that opens a git repository and two database
files under a user's home directory as a side effect of running a pack that
never touches storage is a real, silent behaviour change, not a safety
check. Validating the path string at config load time gives the same
fail-loudly-at-boot property without ever touching the filesystem, which is
the cheaper and correct place for that guarantee to live until an adapter
actually needs to open the path.

## What I still do not understand

Whether the rebuild test would catch a *subtler* stale-row bug than the one
it was built for. It proves two things solidly: nothing is lost across a
full index deletion, and a row for a deleted path does not survive a
rebuild. It does not prove that `Upsert` correctly *overwrites* a row for a
path that still exists but changed shape (e.g. a field renamed or dropped)
across a rebuild — that property is covered by `sqlindex`'s own Task 3 tests
(`Upsert` deletes and re-inserts a path's fields every time), not by
anything here, and I have not connected those two test suites' guarantees
into one statement I am fully confident in.

I also do not think `Record.Fields` being `map[string]string` is the right
long-term shape, but I do not have evidence yet, only a suspicion.
`extractItem`'s `state` field is naturally a string, so it never exposed the
seam. The first real consumer (the job-hunt slice) will almost certainly
want to query on things that are not strings by nature — a posted date to
range over, a numeric score to sort by — and `map[string]string` forces
those into string comparisons or a second parsing step at every read site.
Whether the fix is a typed `Fields map[string]any` with SQLite/DuckDB
storing a type-tagged column, or whether string-only fields are fine and
range/sort queries belong in `duckindex`'s history table instead, is a
question this increment's placeholder extractor was not built to answer,
and I would not want to guess at the richer shape without a real consumer
forcing the choice.
