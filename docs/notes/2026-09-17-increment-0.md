# Increment 0: the tracer bullet

## What the pattern was

A composition root (`cmd/atlas/main.go`) wires config, a tool registry, a
tracer, and a runner; the runner walks a YAML blueprint (`packs/*.yaml`)
calling tools by name. The bet was that this shape needs no `.go` change to
run a new pack — only a new YAML file.

`packs/hn-summary.yaml` proved the bet on the first attempt: it ran with zero
changes to any `.go` or `.yaml` file. That is the increment's binding test
and it passed.

`packs/job-hunt.yaml` did not run unaided. It needed one line changed in
`internal/config/layers.go`: the default model moved from `qwen3.5:9b` to
`qwen2.5-coder:7b`, because the original default could not reliably produce
the JSON that `expect: json` demands for an open-ended judgement call. That
is a config default, not new code or a new code path, but it is still a `.go`
file edit driven directly by a pack's needs, and it should not be undercounted
as "nothing changed."

The `TestCompositionRootInjectsATracer` guard added in this task exists
because the tracer wiring in `main.go` is exactly the kind of thing a later
edit deletes by accident: one line, no compile error, no runtime error, just
silently no more spans. The test checks structure (`WithTracer(` is called,
and the tracer is obtained after `telemetry.Init`), because a real collector
is not available in the test environment and the assertion needs to hold with
or without one.

## What surprised me

The two packs' first real use exposed a gap in the blueprint format that the
format's design did not anticipate: a pack has no way to request a model.
`model.complete` reads the model name from process-wide config
(`cfg.Model.Name`), set once at process startup, not per pack and not per
step. `hn-summary.yaml` wants plain prose and does not care which model
answers. `job-hunt.yaml` needs a model that reliably obeys `expect: json` for
a judgement call with no single correct answer. Both packs are forced to
share one process-wide default, and that tension is the actual reason the
default had to change at all - not a bug in either pack, not a bug in
`model.complete`, but a real hole in what a pack can express. The blueprint
format has no per-step or per-pack model field yet.

The second surprise was in my own process, not the code. The instruction for
picking a new default was "pick empirically, cheapest first." The candidate
list I evaluated against came from the task's controller and did not include
`qwen2.5-coder:1.5b`, which is already installed on this machine
(`ollama list` shows it at 986 MB, next to `qwen2.5-coder:7b` at 4.7 GB -
roughly a fifth the size) and was never tried or ruled out. So "cheapest
first" was really "cheapest among the names I was handed," which is a weaker
claim than the one written down. See below.

## What I would do differently

Before picking a model empirically, enumerate the actually-installed set
myself (`ollama list`) rather than trust a supplied candidate list. The
supplied list is a plausible starting point, not evidence of completeness,
and "cheapest first" only means what it says if the search covers what is
actually available. `qwen2.5-coder:1.5b` should have been tried against
`job-hunt.yaml`'s JSON requirement before settling on the 7b variant; it may
have worked and would have been the cheaper correct answer, or it may have
failed and the 7b choice would then rest on evidence instead of omission.
Either outcome is better than not knowing.

I would also not treat "zero `.go`/`.yaml` changes for `hn-summary.yaml`" as
proof the harness is finished. It proves the harness works for a pack that is
indifferent to model choice and produces unstructured text. It says nothing
about packs that need structured output, multiple models, or retries -
exactly the corner `job-hunt.yaml` hit. One pack passing cleanly is a weaker
signal than it first looks; the second pack is what actually stress-tested
the design, and it needed a code change.

## What I still do not understand

Whether "one model per process" is the right invariant to break now (a
per-step or per-pack model override) or whether it is better to leave the
harness as one-model-per-run and instead push model selection into a routing
layer in front of Ollama, per the Epic 2 plan (vLLM, a second model, retries,
breakers are explicitly out of scope for this increment). Both fix the
format gap; they put the decision at different layers, and I do not yet have
evidence for which layer is the right owner of the choice.

I also do not know how the tracer guard test behaves once a real collector
is available and a run is observed end to end - in this environment nothing
was listening on `localhost:4317`, so `TestCompositionRootInjectsATracer`
is the only thing proving the wiring is correct. The trace itself - a span
named for the blueprint with a child span per step, each carrying a tool
name and step id - was never observed in this increment, only asserted
structurally. That gap should close in the increment where a collector is
actually stood up (`infra/`'s observability stack), not left open
indefinitely.
