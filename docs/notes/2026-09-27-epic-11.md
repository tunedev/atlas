# Epic 11: outcomes and calibration

## What the pattern was

An outcome is not a new document — it is a later revision of the same judgement document.
`app.AttachOutcome` reads the judgement at its existing path, splices a value into the
`outcome` key by byte, and writes back to the same path; `RecordDocument`'s existing
same-path-different-body write makes the new commit, and the index row is replaced, not
appended to. Nothing about "attaching an outcome" is a new kind of record — it is the same
document, later.

Calibration is a derived view, computed fresh from the record on every run and never
written to git, the same way the two indices themselves are disposable
(`docs/design/the-record.md`). `Calibrate` reads recorded answers and attached outcomes
straight off `Docs`/`Index`; there is nothing for a persisted report to go stale against,
because there is no persisted report.

Both are held to the same honesty rule: report the count always, and refuse the number
that count cannot support. `MinSample = 30` gates the headline Brier score, `MinBinSample =
10` gates each reliability bin, and `AgreementRate` uses the same `MinSample` for its own
rate. Below the threshold, `N` (or a bin's own `N`) is still returned; `Brier`,
`ObservedRate` and `Rate` are `nil`. An outcome sorts into one of three dispositions —
positive, negative, or inconclusive (evidence of nothing, such as a ghosted application) —
and a pending, zero-coverage, inconclusive, unclassified or option-mismatched judgement is
excluded and the exclusion is counted by name, never silently dropped — the spec's own four
exclusions plus R2's fifth.

## What surprised me

**R1 — the spec's own `Prediction` used one field, `Positive`, for two different
vocabularies.** The spec's draft matched `Positive` against both `Outcome.State` (what
happened in the world) and an answer's `Distribution` keys (`Positive: []string{"apply"}`,
using `Distribution["apply"]`). Those vocabularies differ — an answer option is `yes` or
`apply`; an outcome state is what happened. Under the spec's own shape, a pack could not
score `stretch = yes` against an outcome state without renaming one of them. The ruling
splits it: `Prediction` gained `Options []string` for the answer options whose mass is the
predicted probability, and kept `Positive`/`Negative` as outcome states, with all three
required non-empty and `Positive`/`Negative` forbidden from overlapping.

**R3 — the byte-preserving splice, and why it had to be a splice.** `AttachOutcome` does
not round-trip the document through `judgementDoc` and re-marshal it. It calls `spliceKey`,
which walks the JSON token by token and replaces only the `outcome` value, leaving every
other key, its value and its order untouched. This was necessary because Epic 11 was
planned and implemented in parallel with Epic 7 (session `atlas-epic-5-56`), which adds its
own optional document keys (`fingerprint`, `rules`) and index fields (`verdict`, `tripped`,
`fingerprint`, `agrees`) to the same judgement documents and rows — coordinated in the
ledger as "additive doc keys... outcome key untouched." A round trip through `judgementDoc`
would silently drop any key that struct does not know about yet, which is exactly what a
concurrently-landing Epic 7 key would be from this branch's point of view. `unit-a-report.md`
proves the necessity directly, by mutation: swapping `spliceKey` for
`doc.Outcome = outcomeDoc{...}; json.MarshalIndent(doc, "", "  ")` and rerunning
`TestAttachingKeepsEveryOtherKeyAndFieldAsItWas` fails because the test's simulated
unknown key, `fingerprint`, is dropped by the round trip:
```
attaching changed more than the outcome value:
before:
{
  ...
  "outcome": null,
  "fingerprint": "abc123"
}
after:
{
  ...
  "outcome": {
    "state": "wet",
    "when": "2026-09-29T09:00:00.000Z",
    "note": "umbrella needed"
  }
}
--- FAIL: TestAttachingKeepsEveryOtherKeyAndFieldAsItWas (0.04s)
```
The measured identity claim in the plan (splicing `null` back in reproduces a
`MarshalIndent` document byte for byte) is why `spliceKey` was trusted to write the *other*
direction with no drift, not just to avoid dropping keys forward.

**R6 — judgements recorded before coverage existed are excluded, and not as a special
case.** `docs/notes/2026-09-24-epic-3-closing.md` already measured that a coverage-0
answer's `1.0` mass "measured nothing" about real competition among a question's options.
R6 applies that same reasoning retroactively: a judgement recorded before `Coverage` existed
at all reads `{Represented: 0, Declared: 0}`, so it satisfies the existing zero-coverage
exclusion without any new code — it is excluded for the same reason a live coverage-0
answer is, not a separate rule. `TestAZeroCoverageAnswerIsExcludedEvenWhenItWasRight` proves
the guard by mutation in `unit-b-report.md`: deleting the `Coverage.Represented == 0` check
turns a judgement that was "right" (`p=1.0`, outcome `wet`) into a scored point instead of
an exclusion — `N = 1 excluded = {...ZeroCoverage:0...}` — which is exactly the falsely
confident number the exclusion exists to prevent.

**The live run: n=3, a clean diff, and a pre-existing quirk that reads oddly until you
trace it.** Task 7 ran three `judge.ask` calls against real Ollama
(`qwen2.5-coder:7b`), attached two outcomes via `judge.outcome`, and ran `judge.calibrate`.
The document diff for one attachment is exactly the outcome slot, nothing else:
```
-  "outcome": null
+  "outcome": {
+    "state": "wet",
+    "when": "2026-11-02T00:00:00.000Z",
+    "note": ""
+  }
```
The calibration output reported `n=3` pooled and per engine, headline `"n=3, too few for a
Brier score (needs 30)"`, and `by_engine` held exactly one entry — but that entry's
`provider` and `model` both read `qwen2.5-coder:7b`. That is not a bug in this epic: `cmd/atlas`
names the `openaiprov` provider adapter after `cfg.Model.Name`, so on this branch
`provider` and `model` are always the same string, and `by_engine`'s grouping key
(`(Provider, Model)`) collapses to one axis in practice. Existing, reviewed Go behaviour,
recorded as a deferred minor rather than fixed here, since fixing it means naming providers
properly at the composition root — outside this epic's scope.

**A first-draft test passed for the wrong reason, and only review caught it.** Task 6's
brief wrote a "no state" subtest (`{"subject_id": "a"}`) meant to exercise `judge.outcome`'s
empty-state guard. It targeted a subject with no recorded judgement at all, so
`AttachOutcomeForSubject` returned `"outcome: no judgement recorded for \"a\""` before
`AttachOutcome`'s empty-state check ever ran — the subtest would have passed identically
with that guard deleted. Review caught it (plan-mandated finding, `task-6-report.md`); the
fix recorded a real judgement for subject `"a"` first, so the subtest reaches the guard it
was meant to test, and added a mutation proof: deleting the guard now fails exactly that
subtest (`no_state`, `err = <nil>`) and no other.

**The spec gained a third disposition mid-implementation, by human ruling.** After this
epic's plan was written, the human decided a ghosted application is inconclusive, not
negative, and updated the spec to a three-way `Positive`/`Negative`/`Inconclusive`
disposition instead of two; the code followed the spec's revision rather than the plan's
original two-way shape.

## What I would do differently

I would write `AttachOutcomeForSubject`'s partial-failure return and `currentRow`'s
no-existing-row fallback as their own tests up front, rather than leaving both untested and
recording them as deferred minors after the fact. Both paths are real and reachable — a
subject with several judgements where a later one fails to write, or an index rebuilt from
git history reaching `AttachOutcome` before the row it should update exists — and neither
is exotic enough to defer twice.

## What I still do not understand

Whether `CalibrateByEngine`'s double read of every matching judgement document (once for
the pooled pass, once again for its own engine's group) is a real cost worth fixing, or
noise below the point where an extra `docs.Get` per judgement matters. It is correct either
way — the deferred minor is about redundant I/O, not a wrong answer — and I have not
measured it against a corpus large enough to know which side of that line it falls on.

## What was deliberately not built

From the spec's own table, unchanged by this plan:

| Out | Why |
|---|---|
| 11.1 Pipeline state per application | Needs Epic 10's drafted/sent vocabulary, which does not exist yet |
| 11.2 Staleness from declared send | Same dependency: staleness is measured from a send declaration that does not exist |
| Automatic outcome detection (email, ATS scraping) | No such adapter exists; its own epic's worth of scope |
| Scoring across mixed question ids in one bucket | A `Prediction` scores one `QuestionID` at a time |
| Automatic classification of which outcome states are Positive/Negative/Inconclusive | Pack-declared, per the vocabulary constraint |
| Widening `TopLogProbs`, rephrasing `choice` options, or the `laya` classifier | Carried over, unresolved, from the epic 3 closing note |
| A second engine's numbers compared automatically | `CalibrateOptions` groups by provider/model; nothing runs a second engine against the same subjects to compare |
| Rejecting or gating on a low `Confidence`/`Coverage` at judgement time | A policy decision, not tracking's job |
| A UI | Epic 12, last, deliberately |
| Persisting the calibration report as a git document | Fully derivable from the record on every run |

Ruled out by this plan:

- **R7 — a provider/model filter on the tool.** `judge.calibrate` always returns both
  `pooled` and `by_engine`, with no filter argument, so a caller cannot narrow the tool's
  output to one engine. `CalibrateOptions` keeps that filter for `Calibrate`'s direct Go
  callers; it just is not exposed through the tool.
- **R8 — the agreement rate's confidence breakdown.** `AgreementRate` reports one rate over
  existing `decision`/`verdict_at_decision` fields; the spec's optional breakdown by
  `Confidence` was not built.

Every deferred minor from the ledger (`progress.md`), none of them blocking:

- `spliceKey` re-encodes a `\u`-escaped key *name* rather than preserving it; values are
  untouched, and no writer in this codebase produces an escaped key name today, so it is
  unreachable rather than fixed.
- Duplicate top-level `outcome` keys in a document are both replaced by `spliceKey`, not
  rejected — a document reaching `AttachOutcome` with two `outcome` keys is not a shape any
  writer here produces.
- `currentRow`'s no-existing-row fallback and `AttachOutcomeForSubject`'s partial-failure
  return (see "What I would do differently") are untested.
- `currentRow`'s `path` parameter shadows the `path` package within its own body.
- `CalibrateByEngine` reads each matching judgement document twice: once for the pooled
  pass, once again per engine group.
- Below-threshold `nil` numbers (`Brier`, `ObservedRate`, `Rate`) are dropped by the
  template sanitiser when a later pack step references them — pre-existing `render.go`
  behaviour; a pack author must not template `.pooled.brier` unconditionally.
- Judgements record `provider == model` on this branch, because `cmd/atlas` names the
  `openaiprov` provider adapter after `cfg.Model.Name`; `by_engine` groups consequently read
  `provider=model`, pre-existing and out of this epic's scope.

## Open for the human

Two questions the spec leaves open, unchanged by this implementation:

- **Which question id a job-hunt pack should name as `Prediction.QuestionID`.** Epic 7's
  verdict shape (apply/stretch/skip, with reasons) is not fixed yet, so this was not this
  epic's call to make; `Prediction` is generic enough to score whichever question the pack
  eventually names.
- **Whether a long-silent `ghosted` should eventually convert to negative.** The spec now
  rules that `ghosted` (with `withdrawn` and `not_applied`) is `Inconclusive`, not
  `Negative` — silence is not a verdict — and `packs/judge-calibrate.yaml`'s header example
  lists all three under its `inconclusive` var accordingly. What is still open is whether a
  long-enough silence should later promote a state from `Inconclusive` to `Negative`, and at
  what threshold; that is left a pack-authoring decision, not a core one.
